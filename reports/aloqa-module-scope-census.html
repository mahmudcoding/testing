What was measured

Every file in both repos was classified into one module, then counted five ways. Generated code (ogen, protobuf — 402k lines of it) and test code were excluded from the product totals.

Measurement What it counts Weight Total
User-visible strings i18n dictionary keys, attributed to a module by which files reference them — the closest proxy for how much a person can actually see and read 25% 3,365
UI components Non-test .tsx components — how many distinct things render 25% 1,227
Frontend code Hand-written non-test lines across packages/features, apps/web features and widgets 20% 278,781
API operations Distinct method + path pairs in the generated OpenAPI contract — how many behaviours sit behind the screens 15% 280
Backend code Hand-written non-test Go, generated code removed 15% 134,175

Two methods, independently, agree. Attributing i18n keys by namespace and by actual code reference were computed separately and land within a percentage point of each other on every module (Calls 34.1% vs 34.8%). That agreement is the main reason to trust the composite.

Where the measurements disagree

Four modules have a wide spread. Each has a cause, and each changes how you should read its number.

Settings0.2% ↔ 10.6%

Almost entirely a frontend module — many screens and controls, but nearly no backend of its own, since it reads and writes through the user and org endpoints. Treat 6.3% as real UI work with very little server behaviour behind it.

Admin & org6.2% ↔ 15.9%

The inverse: heavy backend (roles, permissions, invites, audit), comparatively thin UI. Also note the org-administration screens physically live inside features/settings/, not features/admin/ — the census reassigns them, so this number is higher than the directory layout suggests.

Auth & onboarding1.8% ↔ 9.5%

Small, simple screens sitting on top of a substantial auth service — sessions, tokens, magic links, verification, 2FA. The screens are quick to test; the state machine behind them is not.

Search0.4% ↔ 4.1%

The lowest number here is the least trustworthy in the whole census. Search has a real 46-file UI — filters, tabs, sort, scope chips, result groups — but its strings are hardcoded rather than translated, so the i18n measure badly understates it. Read Search as nearer 3%.

Routes are a trap. Calls occupies just 6 of the app's 51 routes but 35% of its functionality — nearly all of it lives in states inside a single in-call route. Counting screens or URLs to size a module would understate Calls by roughly a factor of five.

Balanced sector splits

A sector is what a session tests; a lane is the isolated fixture set and browser block it runs on. The letters are aligned — sector A is meant to run on lane A — but they are separate things. Bundles are kept coherent on setup cost, so everything needing the multi-browser call rig is concentrated and only the sectors that need it pay for it. The chosen five-sector shape is below; the alternatives after it are balanced purely on scope weight, for comparison.

Unbalanced on scope, balanced on effort — which is the point. The Calls sectors carry 15.7% and 17.2% while the two catch-all sectors carry 23.3% and 22.8%, a 7.6 pp spread. That gap is not a flaw in the split: in-call work costs far more per unit of scope than settings or directory work — three to four browsers, real media, multi-participant state, timing-sensitive checks.

At an in-call cost of roughly 1.45× per unit, sector A's 15.7% comes out at about 22.8 effort-equivalent points, level with sectors D and E. That multiplier is reasoned from the setup burden rather than measured, so treat it as a working assumption — but it means this shape should finish closer to level than the raw percentages suggest.

Within each pair the balance is tight regardless: 1.5 pp between the two Calls sectors, 0.5 pp between the two catch-alls.

Six is where Chat stops fitting in one sector — at 18.8% it exceeds the 16.3% target, so it has to divide the way Calls already does. That division costs more than the Calls one did. In-call and around-call are genuinely different jobs with different rigs; Chat's halves both want the same setup — two browsers and a channel with history — so splitting duplicates the setup without making either sector cheaper, and the border between "message actions" and "channel management" is soft enough that each sector will keep wandering into the other.

Six sectors also means six reports to read and triage in one day, which is usually the binding constraint rather than the testing itself.

Scope is not effort. These weights size how much functionality a sector covers, not how long it takes to cover it. A unit of in-call testing costs several times a unit of settings testing — multiple browsers, real media, timing-sensitive state. If sectors are timeboxed rather than scoped, the in-call sector should get the longest box or the smallest share.

Running a sector

This page is the reasoning behind the split. The working definitions — what each sector covers, where its borders sit, which accounts and browsers it needs, and the filenames it writes — live in SECTORS.md in the QA repo, so a session reads them rather than having a scope pasted into its prompt.

SectorRuns onScopeWrites its files under
A · Calls, inside the calllane A15.7%calls-inside
B · Calls, around the calllane B17.2%calls-around
C · Chatlane C18.8%chat
D · Org, identity & settingslane D23.3%org
E · Workspace content & chromelane E22.8%workspace

A session is started with just a letter. /run-until 14:00 A means sector A on lane A, and nothing more needs saying — the repo's always-loaded instructions send the session to SECTORS.md for the rest. Sector and lane are named separately only when they differ.

This also keeps the timebox clean: it replays whatever task text it was given every time it refuses to let a session stop, so a pasted scope would be re-injected over and over. A single letter is not.
