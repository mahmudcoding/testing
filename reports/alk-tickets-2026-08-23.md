# Звонки Aloqa — заготовки тикетов (23.08.2026)

Один блок = один тикет. Написано простым языком, без тестовых аккаунтов и идентификаторов. Важность: **Medium** — мешает, но обойти можно. **Low** — мелочи: тексты,
переводы, доступность.

---

## 1. [BE][CALLS][SECURITY] Пароль от звонка можно подбирать сколько угодно — попытки не ограничены

**Severity:** Medium · **Area:** backend

**Путь.** `Calls` → `Start now` → `Who can join` → `Password` → задать пароль → `Start call`.
Затем с другого аккаунта: `Calls` → `Join` у этого звонка → несколько раз подряд ввести неверный пароль.

**Описание.** При входе в звонок по паролю количество неверных попыток ничем не ограничено: нет ни задержки, ни временной блокировки, ни капчи. Время ответа не растёт, поэтому пароль перебирается на полной скорости.

**Шаги.**
1. Создать звонок с режимом входа «Password».
2. Из аккаунта участника workspace отправить серию `POST /meeting/{id}/join`
   с неверными паролями, затем с верным.

**Как должно быть.** После нескольких неверных попыток ввод пароля должен притормаживаться или временно блокироваться, чтобы пароль нельзя было перебрать. Достаточно небольшой задержки и лимита попыток на звонок.

**Фактически.** Ограничений нет; верный пароль принимается сразу после серии неудач.

```
10 неверных подряд, затем верный:
 1. неверный -> 400 (147ms) REALTIME_PASSWORD_INVALID
 …
10. неверный -> 400 (138ms) REALTIME_PASSWORD_INVALID
11. верный   -> 200 (160ms)              # принят сразу, локаута нет

40 попыток подряд: totalMs 5828, все 400, avgMs 146, роста времени нет
(~7 попыток/с на один поток)
```

**Влияние.** Ограничено участниками workspace (внешнему пользователю `join` → 403),
но пароль звонка — именно тот барьер, который защищает приватную встречу
от постороннего коллеги.

## 2. [FE-WEB][CALLS][A11Y] Ползунок «Maximum video quality» нельзя настроить с клавиатуры

**Severity:** Medium · **Area:** frontend

**Путь.** В звонке: `Meeting settings` → `Maximum video quality` → встать на ползунок и несколько раз нажать стрелку влево.

**Описание.** Ползунок качества видео реагирует только на первое нажатие стрелки. После него фокус слетает с ползунка, и следующие нажатия ни на что не влияют — чтобы сдвинуть значение ещё на шаг, приходится заново добираться до ползунка табом через всё окно звонка. Мышью всё работает нормально.

**Шаги.**
1. В звонке открыть `Meeting settings`.
2. Сфокусировать слайдер `MAXIMUM VIDEO QUALITY`.
3. Нажать ArrowLeft несколько раз подряд.

**Как должно быть.** Стрелками с клавиатуры значение должно двигаться на каждый шаг, пока ползунок в фокусе, — как это работает мышью. Фокус не должен слетать после первого нажатия.

**Фактически.** Сдвигается только первое нажатие.

```
after focus     value=2  active=INPUT (слайдер)
press ArrowLeft value=1  active=DIV  call-overlay-expanded   # фокус потерян
press ArrowLeft value=1  active=DIV  call-overlay-expanded   # нажатие потеряно
```

Мышью значение меняется нормально. Нарушение WCAG 2.1.1 (Keyboard).
Само ограничение качества работает: после 360p входящее видео падает до 640×360.

## 3. [FE-WEB][CALLS] Вместо причины ошибки показывается «Try again», хотя повтор не поможет

**Severity:** Medium · **Area:** frontend

**Путь.** В звонке, где уже есть несколько участников: `Meeting settings` → `Participant limit` → поставить число меньше, чем участников сейчас → `Save`.

**Описание.** Если организатор ставит лимит участников меньше, чем людей в звонке сейчас, сервер отвечает точной причиной. А в интерфейсе появляется общее «Could not save meeting settings. Try again.» — сколько ни повторяй, ничего не изменится.

**Шаги.**
1. В активном звонке с N участниками открыть `Meeting settings`.
2. Установить `PARTICIPANT LIMIT` меньше N и нажать `Save`.

**Как должно быть.** В интерфейсе нужно показывать настоящую причину: «нельзя поставить лимит меньше, чем сейчас в звонке (столько-то человек)». Кнопка «Try again» тут не поможет и не нужна.

**Фактически.** «Could not save meeting settings. Try again.»

```
PATCH /api/v1/meeting/{id} -> 400
{"key":"REALTIME_MEETING_LIMIT_BELOW_CURRENT","message":"…"}

UI (панель и тост): "Could not save meeting settings. Try again."
```

**Замечание.** Это недоработка именно экрана настроек, а не общий подход:
при попытке впустить участника в переполненный звонок продукт показывает
конкретный текст на `400 REALTIME_MEETING_FULL`.

## 4. [FE-WEB][CALLS] Длинное название звонка — звонок не создаётся, и об этом не сообщают

**Severity:** Medium · **Area:** frontend

**Путь.** `Calls` → `Start now` → вставить очень длинное название (примерно от 130 символов) → `Start call`.

**Описание.** В поле названия звонка нет ограничения на длину, поэтому туда можно вставить сколько угодно текста. Но если название длиннее 128 символов, при нажатии Start call окно просто закрывается: звонок не создаётся, ошибку не показывают.

**Шаги.**
1. `Calls` → `Start now`.
2. Ввести название длиной 129+ символов → `Start call`.

**Как должно быть.** Либо в поле нельзя ввести больше положенного, либо при слишком длинном названии показывается понятная ошибка, а окно остаётся открытым — чтобы человек исправил название. Молча закрываться окно не должно.

**Фактически.** Окно закрывается, звонок не создаётся, ошибку не показывают.

```
len=128 -> POST /api/v1/meeting 200   звонок создан
len=129 -> запроса нет                звонок не создан, ошибки нет
len=300 -> запроса нет                звонок не создан, ошибки нет
```

## 5. [FE-WEB][CALLS] Заходишь в звонок со второго устройства — на первом пишет «Call ended», хотя звонок идёт

**Severity:** Medium · **Area:** frontend

**Путь.** Войти в звонок на одном устройстве → войти в тот же звонок тем же аккаунтом на втором устройстве → посмотреть на экран первого устройства.

**Описание.** Если зайти в один и тот же звонок с двух устройств под одним аккаунтом, второе подключается, а первое из звонка выходит — это нормально. Но на первом устройстве появляется окно «Call ended» с подписью «Finalizing call details…», хотя звонок никуда не делся: прямо за этим окном он показан как идущий.

**Шаги.**
1. Войти в звонок с устройства A.
2. Войти в тот же звонок тем же аккаунтом с устройства B.
3. Посмотреть на экран устройства A.

**Как должно быть.** На устройстве, которое вышло из звонка, должно быть написано что-то вроде «вы подключились с другого устройства» — а не «звонок завершён». Человек должен понимать, что звонок продолжается на втором устройстве.

**Фактически.** «Call ended», хотя за оверлеем в том же окне звонок отображается
как `LIVE`, а API возвращает `status: "active"`.

```
устройство B: POST /meeting/{id}/join -> 200, PeerConnection connected
устройство A: call surface закрыт, PeerConnection закрыт
  диалог: "Call ended | Finalizing call details… | Done"
  на фоне того же экрана: звонок всё ещё LIVE
  GET /api/v1/meetings/current -> "status":"active"
```

## 6. [FE-WEB][CALLS] При включённом Push to talk микрофон не работает обычной кнопкой, и пользователю не объясняют почему

**Severity:** Medium · **Area:** frontend

**Путь.** `Settings` → `Calls and audio` → включить `Push to talk` → войти в звонок → навести курсор на кнопку микрофона.

**Описание.** Если включить Push to talk, кнопка микрофона в звонке становится неактивной — говорить нужно, удерживая пробел. Но подсказка на кнопке по-прежнему обещает переключение микрофона по ⌘D, и этот шорткат тоже не работает. Нигде не написано, что микрофон теперь на пробеле.

**Как должно быть.** Пока включён Push to talk, у кнопки микрофона должна быть понятная подсказка — например «говорите, удерживая пробел», — а не обещание переключения по ⌘D, которое не работает.

Сам Push to talk работает корректно.

## 7. [FE-WEB][CALLS] В блоке «Live now» у личного звонка неверное число участников и чужое название

**Severity:** Low · **Area:** frontend

**Путь.** `Directories` → `People` → `Call` напротив человека → собеседник принимает вызов → оба открывают `Calls` и смотрят на карточку в блоке `Live now`.

**Описание.** Когда в личном звонке двое, карточка показывает «1 participant» и только один аватар — собственный, теряя второго человека, хотя рядом же написано, кто ведёт звонок. Название показано как «Team meeting», а кнопка предлагает войти в звонок, в котором человек уже находится.

**Как должно быть.** В карточке личного звонка должно быть правильное число участников (двое — значит «2 participants»), настоящее название звонка и оба аватара. Если человек уже в этом звонке, кнопку «войти» показывать не нужно.

```
API: meetings/active -> participant_count: 2, оба участника в top_participants
DOM: "Live now | LIVE | Team meeting | 1 participant · hosted by …"
```

Состояние стабильное. Для групповых звонков счётчик корректен; после завершения
тот же личный звонок в Recent calls подписан правильно и попадает в фильтр
`1-to-1`. Дефект локализован в live-карточке личного звонка.

**Не дубль ALK-3324:** там счётчик *не уменьшается* после выхода участника;
здесь он *занижен* при двух активных.
