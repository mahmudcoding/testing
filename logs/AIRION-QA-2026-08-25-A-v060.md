## Findings

### BUG-1 [Medium] [frontend] Unsaved Settings edits are discarded silently — no warning on any exit path

**Where:** Settings → Account (`/w/{ws}/settings/account`), Contact details card.
Reproduced 2/2 on separate loads.

Type a value into **Phone** (field starts empty). A sticky save bar appears at the bottom reading
`2 unsaved changes` / `Discard` / `Save changes` — so the app *knows* the form is dirty and says so.
Then leave without saving. In **every** exit path the typed value is dropped with no prompt:

| exit path | dialog shown | value on return |
|---|---|---|
| click another Settings section (Appearance/Profile), then back to Account | none | `""` |
| click out of Settings entirely (→ `/chat/mentions`) | none | `""` |
| hard reload (`page.reload`) | no `beforeunload` prompt | `""` |

Measurement (run 2): dirty `phone="+998901110001"`, `saveish=["Discard","Save changes"]` →
after nav to `/settings/appearance` `dialogs=[]` → back on `/settings/account` `phone=""`.
`beforeunloadPrompt=false` on reload.

**Как должно быть:** either keep the entered values when returning to the section, or warn before
leaving ("You have unsaved changes"). Showing a bar that says *2 unsaved changes* and then discarding
them without a word is the worst of both.


### BUG-2 [High] [backend] Turning off "Active status" does not hide presence from anyone who already has the app open — the server emits the correct hide event and then immediately cancels it

**Ticket this belongs to:** ALK-2964 `fix(settings): make Active status hide presence` (v0.60.0).
**Where:** Settings → Profile → Availability → **Active status**
("Show your online status to members of your workspace.")

**Repro (2 accounts, both windows already open):**
1. Bob has Aloqa open; Alice's avatar dot in his **Direct messages** sidebar is green.
2. Alice: Settings → Profile → Availability → turn **Active status** off → **Save profile**
   (request `PUT /api/v1/users/me/presence-settings/update {"hide_presence":true}` → `200 {"ok":true}`).
3. Watch Bob's window without reloading.

**Result:** Alice's dot stays **green** (online) indefinitely. Only when Bob reloads does it turn grey.

**Measured — WS frames received by Bob** (recorder installed via `page.addInitScript` before load,
socket `wss://airion-cargo.store/ws/chat`). Two frames arrive back-to-back on the OFF flip:

```
{"type":"presence.update","user_id":"<alice>","online":false,"last_seen_at":"2026-08-25T07:43:17.952486624Z"}
{"type":"presence.update","user_id":"<alice>","online":true}
```

The first is correct; the second immediately contradicts it. The UI faithfully renders the **last**
frame, so Alice goes back to green. The second frame carries no `last_seen_at`, i.e. it comes from a
different producer than the hide event.

**Not a slow-propagation issue:** after the pair, **75 s of idle produced 0 further presence frames**
(`newFrames:3`, all `pong`), and Alice's dot was still `rgb(19, 122, 58)` at the end.

**Direction matrix (measured):**

| action | frames pushed to an open viewer | viewer sees | server truth on reload |
|---|---|---|---|
| Active status **OFF** (`hide_presence:true`) | `online:false`, then `online:true` | stays **green** — wrong | grey — correct |
| Active status **ON** (`hide_presence:false`) | **none** (only `pong`) | unchanged until reload | green — correct |

Measured dot colours: online `rgb(19, 122, 58)`, offline/hidden `rgb(138, 149, 163)`.
Bob's tab was `visibilityState: "visible"` throughout (not a throttled-pane artefact).
Confirmed over two OFF flips and one ON flip; 13 s and 60 s polls plus the 75 s idle watch.

**Why [backend]:** the contradictory `online:true` is server-emitted, and the server's own REST truth
(what a reload renders) is correct. The web client is rendering the last event it was given.

**Как должно быть:** when a user turns off "Show your online status", everyone currently looking at
them should see them go offline right away, without reloading — and no later event should put them
back online while the setting is off. Turning the setting back on should likewise show them as online
to open sessions.

**Impact:** this is a privacy control. In a chat app people keep the tab open for hours, so the
population for whom the setting silently does nothing is most of the workspace.


### BUG-3 [Medium] [frontend] After one send fails, later messages are shown as delivered while nothing is sent — and when the queue flushes they arrive out of order

**Ticket this belongs to:** ALK-2958 `fix(chat): prevent failed sends from wedging queue` (v0.60.0).
**Where:** any channel composer. Reproduced 2/2.

**Repro** (`#qa-general`, one account):
1. Make sends fail: `page.route('**/api/v1/messaging/messages', r => r.abort('failed'))`.
2. Type message **A**, Enter. Correct: renders with **"Could not send the message. Try again."**
3. Remove the block (`page.unroute`), wait, then type message **B**, Enter.

**Result for B — measured:**
- **No HTTP request is made at all** — recorder on `POST /api/v1/messaging/messages` gave `netAfterB: []` over 8 s.
- B renders in the channel with **no pending and no error indicator** (`B_anyError: null`).
- B is **not on the server**: `GET /messaging/channels/<ch>/messages?limit=100` -> `hasB:false`.

For about a minute the user is looking at a message that appears sent, is not sent, and says nothing.

**It does recover — nothing is lost:**

| checkpoint | A on server | B on server | requests seen |
|---|---|---|---|
| right after sending B | no | no | none |
| +60 s idle | no | **yes** | 1 x `req` -> `resp200` |
| after a reload | **yes** | yes | - |
| new message typed post-reload | - | - | `req` -> `resp200`, on server at once |

**Ordering ends up wrong.** A was typed **before** B but lands **after** it, stamped with the retry
time instead of the compose time. Rendered order after reload:

```
12:55  V60-FAIL-44507 should-fail
12:57  V60-B-44619 after-restore     <- typed second
12:58  V60-A-44613 blocked           <- typed first, delivered last
```

That is the persisted order everyone in the channel sees, not a local artefact.

**Kak dolzhno byt (RU in report):** a message waiting to be sent should be shown as pending rather than
as a delivered message; the queue should retry promptly once the connection is back instead of sitting
idle for about a minute; and messages should arrive in the order they were written.

**Rig check:** failure induced with Playwright routing per repo guidance; `page.unroute` confirmed
effective (a message typed after reload sent immediately, `req`->`resp200`); tab `visibilityState:
"visible"` throughout. One account, sequential actions - not a two-actor race.


### BUG-4 [Medium] [backend] An invited participant cannot see who else is in a meeting - the panel reads "Participant list unavailable"

**Ticket area:** ALK-2759 / ALK-2777 / ALK-2842 `fix(calendar): make participant truth authoritative` (v0.60.0).
**Where:** Calendar -> click a scheduled meeting -> details dialog.

**Repro:** Alice schedules a meeting and invites Bob (public meeting, `is_private:false`). Bob accepts.
Both open the same meeting from the calendar.

| | organizer (Alice) | invited attendee (Bob, accepted) |
|---|---|---|
| dialog body | `Scheduled by You` **`QA Bob optional Yes Responded Aug 25, 2026, 13:03`** | `Scheduled by QA Alice` **`Participant list unavailable`** |
| `GET /api/v1/calendar/meetings/<id>` | `200`, body 1076 b | `200`, body 661 b |
| top-level JSON keys | `["meeting","attendees"]` | `["meeting"]` |
| `attendees` | array, len 1 | **key absent** (`undefined`) |

Both clients issue exactly the same single request on open
(`GET calendar/meetings/<id> -> 200`; full request list captured, nothing else differs, no 4xx/5xx
anywhere). The server simply omits `attendees` for a non-organizer, and the UI honestly reports it as
unavailable.

**Why this reads as a defect rather than a deliberate privacy rule:** the meeting is public
("Anyone in the workspace can join"), Bob is an invited attendee who has accepted, and the wording
"Participant list unavailable" describes a failure, not a permission boundary.

**Supporting observation (same payload):** `participant_count` is **`0`** for both users even though
the meeting has one accepted attendee - written up separately as **BUG-5**, since it also surfaces on
the Calls hub.

**Refinement found in the second pass — the same string also serves as the empty state.** Swept every
meeting the organizer owns:

| meeting (all owned by the viewer) | `attendees` in the detail response | organizer sees |
|---|---|---|
| 0 attendees | **key absent** | **"Participant list unavailable"** |
| 1 attendee | array, len 1 | the participant list |
| 0 attendees (future, freshly created) | **key absent** | **"Participant list unavailable"** |

So the backend omits `attendees` both when the viewer may not see it and when there is nothing to see,
and the client renders one string for both. The organizer of a meeting nobody has been invited to is
told the list is *unavailable* — i.e. broken — when the truth is simply that it is *empty*. That widens
BUG-4: the message is wrong for a non-organizer (they are being denied, not failing) and wrong for an
organizer with no invitees (nothing is broken).

**Kak dolzhno byt (RU in report):** someone invited to a meeting should be able to see who else was
invited and who has accepted. If some of that is deliberately restricted, the panel should say so
plainly instead of reporting the list as unavailable.

### BUG-6 [Medium] [frontend] The Mentions list shows raw markdown escapes and the unresolved handle instead of the message as written

| surface | shows escapes? |
|---|---|
| Mentions | **yes** |
| Saved Messages | no |
| Channel / DM sidebar previews | no |
| Notification bell | no |

`mention_user_ids: ["U4QABOB00000001"]` - so this is presentation only; clicking **Go to message**

**Kak dolzhno byt (RU in report):** the Mentions list should show the message the way the channel does -

### Sixth pass — the receive-side quality ladder (the gap I had wrongly written off)

My earlier note said the quality ladder needed encoder pressure. That is true only of the **publish**
side (ALK-3278). The **receive** ladder needs nothing but a small tile, which is easy to create with
`Emulation.setDeviceMetricsOverride`. Two-party call, remote publishing 1080p VP9 `L3T3_KEY`.

- **Remote video ceiling is sized in device pixels (ALK-3279, #2567), judged against the layers the SFU
  actually sends (ALK-3323, #2598), and not re-requested for a rung already held (ALK-3284, #2566)** —
  shrank the viewport in steps and read the received `frameWidth` each time:

  | viewport | DPR | tile **device** px | received width | rung |
  |---|---|---|---|---|
  | 1920 | 2 | 3772 | **1920** | top |
  | 900 | 1 | 866 | **960** | middle |
  | 640 | 1 | 606 | **480** | bottom |
  | 420 | 1 | 386 | **480** | bottom — *unchanged* |
  | 1920 (restored) | 2 | 3772 | **1920** | top — recovered |

  Three observations, one experiment: the rung tracks **device** pixels (866 device px picks the 960
  rung, not an 866-sized stream); every landing point is a real spatial layer of the `L3T3` ladder
  (1920 / 960 / 480), not an arbitrary size; and shrinking 606 -> 386 did **not** change the request,
  i.e. it did not ask again for the 480 rung it already had. It also climbs back cleanly.

- **A transport unsubscribe is not reported as an unpublish (ALK-2949, #2456)** — both halves measured:

  | what happened | received width | UI claim about the other participant | video elements |
  |---|---|---|---|
  | tile shrunk to 360 px viewport (rung change only) | 1920 -> **480** | **no** unpublish claim | 2, unchanged |
  | remote genuinely turned the camera **off** | stream ends | **"QA Alice turned camera off"** | 2 -> **1** |
  | remote turned it back **on** | restored | **"QA Alice turned camera on"** | 1 -> **2** |

  `framesDecoded` stayed monotonic across all of it (5408 -> 5768) and the inbound stream never dropped
  to zero during the rung change. So a rung change is silent, a real unpublish is announced — which is
  exactly the distinction the fix is about.
- **Subscriptions follow engine state, not stale reconciler memory (ALK-3287, #2576)** — supported by
  the same run: the rung tracked actual demand in **both** directions and recovered to the top rung
  after the viewport was restored, with no stale intermediate state.

"rig-blocked" was wrong as written — it applies only to ALK-3278 (publish-side CPU pressure), and the
receive-side ladder was fully testable all along.


### Seventh pass — publish-side adaptation, with content the encoder cannot cheat

The earlier "rig cannot create encoder pressure" note was only half right. The blocker was not the
throttle, it was the **content**: Chrome's default fake camera is a flat moving pattern that VP9
compresses almost for free. Replacing it with high-entropy noise changes the picture entirely.

Generated `1280x720`, 2 s, 30 fps of per-pixel random noise with ffmpeg
(`nullsrc,geq=random(1)*255`) into the publisher's rig profile, so `launch.sh` picks it up via
`--use-file-for-fake-video-capture`, and restarted that browser. Then measured outbound video while
stepping `Emulation.setCPUThrottlingRate`.

| phase | resolution | fps | `qualityLimitationReason` | `scalabilityMode` | `qualityLimitationDurations` |
|---|---|---|---|---|---|
| baseline (noise) | — | — | **bandwidth** | **`L3T3_KEY`** | `bandwidth 29.8, cpu 0, none 0.45` |
| CPU 4x | **640x360** | 9 | bandwidth | **`L2T3_KEY`** | `bandwidth 51.9, cpu 0` |
| CPU 12x | 640x360 | 10 | bandwidth | `L2T3_KEY` | `bandwidth 73.9, cpu 0` |
| CPU 20x | 640x360 | 10 | bandwidth | `L2T3_KEY` | `bandwidth 95.9, cpu 0` |
| throttle released | 640x360 | 10 | bandwidth | `L2T3_KEY` | `bandwidth 113.9, cpu 0` |

- **The publish ladder adapts (ALK-3278, #2563 — mechanism verified).** The encoder dropped a whole
  spatial layer, `L3T3_KEY` -> **`L2T3_KEY`**, and settled at **640x360** instead of the source 720p.
  This is the adaptive publish path doing exactly what it is for. Earlier passes never saw it only
  because the default test pattern is too cheap to encode to ever constrain anything.
- **`qualityLimitationReason` is fully exercised (ALK-2427, #2586).** It is not merely present: it
  *changes* (`none` -> `bandwidth`) and the companion `qualityLimitationDurations` attributes the time
  by cause with real accumulating values (`bandwidth` 29.8 -> 113.9 s).
- **Honest limit that remains:** the constraint that bound was **bandwidth**, not **cpu** —
  `cpu: 0` for the whole 113 s even at 20x throttling. Raw noise at 720p30 is ~330 Mbit/s, so the
  bitrate ceiling binds long before the encoder does. The *CPU-specific* branch of ALK-3278 is therefore
  still unexercised; what is now proven is that the ladder adapts and attributes the cause correctly.
  Reaching the cpu branch would need cheap-to-send but expensive-to-encode content, i.e. a genuinely
  loaded machine — not something to induce on the user's laptop.
- It also did not climb back after the throttle was released, which is consistent: the bandwidth
  constraint is still present because the source content is still noise. Not a defect.

**Cleanup:** the 79 MB `video.y4m` was removed from the rig profile afterwards, so the publisher is back
to the default synthetic camera.

|---|---|---|
| workspace member | host | **"QA Bob is typing…"** |
| workspace member | **guest** | **"QA Bob is typing…"** |
| **guest** | host | **nothing** |

The detector diffs *every visible leaf node* in the chat panel against a baseline, so an indicator
cannot hide behind a text match: when the member typed, the new leaf `QA Bob is typing…` appeared and
also showed up in an `aria-live` region. When the guest typed, the only new leaf was the delivered
message's timestamp (`15:59`) — no typing leaf, and nothing typing-related in any live region.

The guest's message itself delivers normally (`V8 Visitor 815 (Guest) · 15:57 … hello from the guest`),
so this is specifically the typing signal not being emitted on the guest's behalf.

**Kak dolzhno byt (RU in report):** while a guest is composing, everyone else in the call should see
"<name> is typing…", the same way they do for a workspace member.

**Dedup:** nothing in the open ALK bug list covers it (`grep "typing"` returns only closed items,
incl. ALK-110 the original backend implementation). Not in either of today's other lane reports.

Admin permissions и Make co-host"* (**Backlog**) appears **stale** — measured earlier in this session,
