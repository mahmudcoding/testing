# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this repository.

## What this repo is

A QA workspace for black-box testing **Aloqa**, the team-chat app at https://airion-cargo.store. This repo holds no application source and no build/lint/test tooling — the work is driving the live app through browser tools, recording findings, and publishing a report. Nothing here is meant to be built. **The product's source is available**, cloned outside this repo — see **Upstream** below for what it is for and what it is not for.

**Scope: what a user can see and do.** Every test is something reachable through the interface — a click path a person could follow. API calls are instrumentation and proof for those paths (measuring the request behind a button, checking a boundary a user could hit), never the subject of testing on their own. Surfaces with no UI — background jobs and tickers, service-to-service gRPC, webhook handlers, endpoints no screen calls, migrations — are the developers' job, not this one. An endpoint no screen reaches is out of scope even when it is clearly untested.

Contents:

- `SECTORS.md` — **the** sector map, and the only one: nine sectors **A-I** covering the whole product, three of them Calls. It gives which part of the product each **sector** covers, the `<area>` token each one writes its files under, and which already-published reports are that sector's dedup targets. The sector letter *is* the lane letter. If the prompt names a sector, read that sector's section — its list marks the sector's boundary against the others, not a checklist of what to test, and is not exhaustive: an unnamed surface inside the sector is still yours.
- `logs/AIRION-QA-<date>-<lane>-<area>.md` — **the session log**: the running bug log for one session (raw, one `### BUG-N [Severity] [backend|frontend] title` block per finding, plus "Verified working" sections). Referred to below as *the session log*.
- `.playwright-mcp/` — auto-generated Playwright MCP snapshots/screenshots/console logs. Disposable; don't read through it for context.
- `reports/findings/<id>.md` and `reports/runs/<date>-<lane>-<area>.md` — **the source of a report**, Markdown with flat frontmatter. A finding is a file; a run lists the findings it publishes. `scripts/render_report.py` turns a run into HTML in `build/` (gitignored), and that file is what you publish with the Artifact tool. **It refuses a run it cannot publish honestly** — one whose `findings:` list names something unpublished, or that lists nothing at all. Withdraw a finding and its run stops rendering until you take the id out; `--force` publishes what remains, and applies to every run in that invocation rather than one. Other runs in a `--all` render are unaffected by the refusal. Record the resulting URL in the run's `artifact:` field and in `reports/README.md`, so a later session can pass it back as `url` and update in place; publishing without `url` creates a separate artifact. The tool can delete an artifact's *assets* but not the artifact itself — removing one is manual, via the claude.ai artifacts gallery. The shared stylesheet is `reports/tools/report.css`, inlined at render time — never copy it into a report.
- `seed/` — fixture seeder for staging (`seed.sh`, `seed_qa_fixtures.py`); see "QA fixtures".
- `verifications/` — what a person judged, one file per day: `verification-<date>.md` from Review's File → Save Record (overwrites and regenerates from the whole current state, so pressing save twice costs nothing; names the report files and sha1s it judged against), `verification-<lane>-<date>.md` from `scripts/verify_run.py` (appends one session block per run, and a run that records no verdict writes nothing).
- `scripts/hooks/` — project hooks. `sector_context.py` runs on every prompt and expands a named sector into its scope from `SECTORS.md`, injecting that sector's section and its exact filenames; silent when no sector is named, and fails open. `scripts/verify_sector_hook.py` is its selftest — 65 checks, each rebuilding the failure it guards against.
- `scripts/` — helper scripts. `jira_cache.py` mirrors the whole ALK project locally so ticket lookups cost no Jira calls (see Reporting); `jira.py` files and comments; `jira_api.py` is the REST transport both use; `callrig/` drives real WebRTC calls (see "Call testing rig"); `bench.py` serves Review and drives a finding's snippet; `findings.py` is **the one parser** — every tool reads findings through it and nothing reads HTML; `render_report.py` turns a run into publishable HTML; `verify_report.py` validates the source against the schema and `verify_report_selftest.py` negative-controls it by mutating a finding twenty-five ways and requiring each to be caught *by its own check*; `check_repro.py` and `verify_snippets.py` check the repro snippets statically and by running them (see Reporting).
- `macapp/` — Review, the Mac app a person judges findings in. `build.sh` builds it into `~/Applications`; the chrome is AppKit and only the detail pane is the page in `reports/tools/bench-ui.html`.

## Upstream: the product repos

Source for the app under test, both private and readable with the local `gh` login:
`AmirkhonMakhkamov/aloqa-frontend` (TypeScript pnpm monorepo) and `AmirkhonMakhkamov/aloqa-backend` (Go).
Cloned at `~/Projects/aloqa-src/{aloqa-frontend,aloqa-backend}` — outside this repo, so nothing here tracks them.

**Read source at the deployed sha, never from the working tree.** The clone is a shared checkout that may sit on any branch, and `git pull` does not fix that — on a feature branch it advances the feature branch and diverges further from the release. Take the sha from the build stamp and read at it:

```
git show 'c4b5386b4a3a:apps/web/src/lib/routes.ts'      # note the quoting, below
git grep -n "SYMBOL" c4b5386b4a3a -- packages apps
```

- **A cause is only «Подтверждённая» if it is a measurement of the running build, or a citation read at the deployed sha.** A conclusion resting on a live response cannot be poisoned by a stale checkout; one resting on `git grep` can. Where a finding can be built on a response instead of on source, build it on the response — the citation sharpens a finding, it should not be what holds it up.
- **A sha-addressed read is unaffected by the branch the clone sits on** — `git show "${SHA}:path"` resolves the commit out of the object store, so the frontend clone being on a feature branch 33 behind deployed does not touch a citation taken that way. The branch only matters for **ref**-addressed operations, and they fail silently: `git grep`, `sed -n` over the worktree, a line number read at `HEAD`, and — the one that bites hardest — **`git log --all --grep=ALK-NNNN`, which walks local refs only and returns empty for tickets whose fix is in the deployed history.** Seven tickets in a row came back empty that way, which reads exactly like "no fix commit exists". Search from the sha: `git log <deployedSha> --oneline --grep='ALK-NNNN'`. **And give any empty grep a positive control before believing it** — `git log <sha> --grep='ALK-' | head -3` proves the mechanism can find anything at all, the same discipline as an empty element list. **A grep that returns a *contradictory* count needs the same suspicion** — one session's `grep -rn "\"$t\"\|$t"` returned a number that disagreed with a finding they had already verified, because BSD grep on macOS does not read `\|` alternation the way GNU grep does. Prefer `-E` and an explicit pattern over BRE alternation here. Note also that **a ticket id in a commit message is not a fixed/not-fixed signal in either direction**: tickets with no referencing commit in deployed history have been verified fixed on the build, so a commit grep cannot carry a staleness metric. Frontend citations therefore have a real anchor; use it and the problem does not arise.
- **The backend has no deploy stamp, so no backend citation is resolvable by the reader — and switching from a line number to a symbol name does not fix that.** A symbol can be absent from `origin/main` entirely (`MeetingEventTypeRecording*`: 5 files on `dev`, 0 on `origin/main`) and fails exactly as badly as a wrong line. Symbol-over-line only survives *drift* (`FileAccessDenied` is line 236 on `dev`, 227 on `origin/main`); it does nothing about *existence*. **What makes a backend cause hold is verifying it on every branch the clone has and saying which** — `grep -rn 'the.exact.string' --include='*.go'` returning zero on both `dev` and `origin/main` is a claim no checkout can knock down. **But check the file before doing any of that work: the drift is per-file, not per-branch.** `git diff --quiet HEAD origin/main -- <file>` turns "possibly stale" into yes/no in one command, and a file that never moved cites safely by line whatever the branch counts say. `dev` being 36/20 off `origin/main` says nothing about whether *your* file moved — that check is what separates a real problem (a symbol on `dev` and nowhere else) from a false alarm (a byte-identical file with alarming branch arithmetic behind it). Better still, build the cause on a measurement and let the source only supply a negative.
- **Check drift in both directions.** `git log <deployed>..HEAD` returning empty means HEAD is *behind*, not current — that one-directional check reports "up to date" for a clone that is 33 commits stale. One command answers it: `git rev-list --left-right --count HEAD...<deployed>` prints ahead and behind together.
- **Quote the ref.** With the sha in a variable, `$S:path` and `"$S:path"` both break in zsh: the character after the colon is read as a history modifier, so `apps/` triggers `:a` (absolute path, eats the sha's last character), `tests/` triggers `:t`, and `src/` fails with "bad substitution". `packages/` happens to work, so validating the technique there proves nothing. Use `${S}:path` or `"$S":path`. The failure reads exactly like "this file does not exist at that sha".
- **An empty `sed` range looks like an absent file.** `git show <rev>:<path> | sed -n '40,62p'` prints nothing when the range is past the end. Confirm with `git ls-tree -r --name-only <rev> | grep <path>`.

- `packages/features/` — `admin calendar calls chat files search settings` — maps almost 1:1 to product areas, so a diff tells you what to test. Commit messages carry ALK ids (`fix(calls): … (ALK-3359)`), so `git log <lastTestedTag>..HEAD` names exactly which tickets are waiting on verification.
- **The build stamp is a source revision.** `data-dpl-id="vX-Y-Z-rc-N-<sha12>"` is tag `vX.Y.Z-rc.N` at frontend commit `<sha12>` — dots become dashes, the trailing 12 hex chars are the commit. So the stamp recorded at session start is the base for `git log <deployed>..HEAD`, and `git merge-base --is-ancestor <tag> <deployed>` answers whether a release is on staging at all. Frontend releases are tagged `vX.Y.Z` and `vX.Y.Z-rc.N`, with a duplicate `web-vX.Y.Z` on the release merge; the backend has `vX.Y.Z` only.
- Use the source to decide **where** to look and to add a root-cause pointer to a ticket (ALK tickets often carry a `Precise root cause` section naming files and lines). Don't derive expected behaviour from it — the testing itself stays black-box.
- **For a finding about a gate, a guard or a permission check, read the comment above it — but only after you have measured the behaviour.** This codebase documents intent at exactly those points, and a comment stating the intended rule beside code that does not implement it is the strongest evidence a finding can carry: one gate's comment says the rule is "quoted rather than guessed" from the backend while the quotation omits a layer the catalogue advertises and the server answers 200 for; another cites the ticket that fixed the identical defect for the neighbouring permission. **The ordering is what keeps this black-box.** The comment explains a defect you have already demonstrated; it is never the evidence for one. Reversed — reading comments to find defects — it becomes guessing at the authors' intentions, which is the thing deriving expected behaviour from source is forbidden for.
- Source widens *where to look in the UI*, not what counts as testable: it does not pull headless surfaces into scope (see **Scope** above).
- **Where the backend sends an enum and the frontend maps it, the two lists are a contract nobody checks.** Extract both at the deployed sha, sort, and `comm -23` them — it surfaces a whole category at once rather than one string at a time. Run it in both directions and read the extraction **in context, not as a list**: the technique's output is a location, not a set of strings, and what is *absent* from the list can be the finding (one gate ORs a read permission with an act permission while the gate beside it has no second operand). Exclude `*_test.go`, extract by emission function rather than string shape — one constants file can feed a WS broadcast, an audit row and a headless outbox — and check candidates against the whole backend, since the producer may sit in a service you did not extract from.
  **Then apply the only thing that decides any of it: no user-visible consequence, no finding.** A diff result dies in at least three ways that all look identical — the key travels on another transport, the fallback is a deliberate category label, or a live arm of the same branch covers the dead one. Chasing the modes is wasted effort; ask instead whether a screen is demonstrably missing something a user should see. A recorded call's log that can never say the recording stopped clears that bar; ten dead strings beside ten working features do not. **The gate has a second exit: no new finding, but possibly a cause for one you already have.** A dead branch beside a working feature still tells you which fields the screen actually depends on. One sector's `end_reason` diff led to the resolver behind a finding they had already published, turning a cause inferred from behaviour into a cited resolver plus a counted response — the reader can now check "83 of 83" without opening the app.
- **The backend's `message` field is never shown to a user, so a Russian string in a response body is not an i18n finding.** Envelopes come back in Russian regardless of account language, and mixed inside one string — `"parent message not found: сообщение не найдено"`. `packages/core/src/api/errorPresentation.ts` resolves exact key → domain prefix → HTTP status → generic and never consults `error.backendMessage`; its own comment calls that "untranslated debug prose" and says preventing its display is what the module exists for. `apiErrorToast.ts` takes only `trace_id`. So check whether a **dictionary** string is wrong, not the envelope. The corollary *is* worth testing: a key absent from `BACKEND_ERROR_TRANSLATION_KEYS` falls to a generic message plus a trace id, which is the mechanism behind every "the screen just says Try again" finding.
- When a screen shows a 500 or a generic error, two files explain what it should have been: `platform/pkg/apperror/keys.go` (backend) lists every error key, and `apps/web/src/generated/openapi.json` (frontend) is the generated contract for the request behind the screen. Use them to root-cause what you saw, not as a list of things to go test.
- Clone with `--filter=blob:none` if disk matters — a full backend clone is 1.4 GB.

## QA fixtures — use these accounts, don't create new ones

`seed/seed.sh` seeds a permanent, isolated fixture set on staging. It is idempotent: re-run it any time the data looks wrong and it repairs drift rather than duplicating. `seed/seed.sh --verify` reports state without writing. You should never need to hand-create QA users again.

**`seed.sh` repairs `company_members` and `workspace_members`, so a kick is reversible** — remove an account from the workspace and then the company, and one `seed/seed.sh --lanes <letter>` puts both memberships back. It does **not** touch `avatar_url` on companies or workspaces: that column is absent from its upserts, so a test avatar is permanent and only a direct DB write clears it.

It auto-creates a venv at `~/.cache/aloqa-qa-venv` (psycopg + bcrypt); override with `QA_VENV=/path ./seed/seed.sh`.

To add a user or channel, edit the `USERS` / `CHANNELS` / `ROLES` lists at the top of `seed/seed_qa_fixtures.py` (fixed IDs, 15 chars: prefix + 14 base36) and re-run — existing rows are untouched. Pin IDs only for things referenced by name (users, channels, roles, company, workspace); let membership and permission rows take their table defaults — deriving those IDs by hand collides, and the `(scope, user)` unique keys already make them idempotent.

**Parallel sessions — lanes.** `seed/seed.sh --lanes B,C` creates further isolated fixture sets, each with its own company, workspace, eight users, channels and roles, so sessions can run at the same time without touching each other's rows. A **lane** is this — fixtures plus the browser port block. What a session *tests* is a **sector** (`SECTORS.md`); the letters are aligned — sector A runs on lane A, sector I on lane I — but the two are separate things, and a prompt may pair them differently. **Nine lanes are seeded, A-I, one per sector**; lane J carries no sector and is free for bugfixes and one-off work, and is the last lane inside the 9220-9319 port window `launch.sh` counts for its global browser cap. Lane A is the set above and keeps its original ids. In lane *X* the ids carry the letter (`U4QA…` → `U4QX…`), emails gain an infix (`qa.owner@` → `qa.x.owner@`) and usernames likewise (`qa_owner` → `qa_x_owner`); display names, channel names and the password are identical in every lane, so the same selectors and driver snippets work in any of them. `seed/seed.sh --verify --lanes A,B,C` checks them all. One lane per session, and give each session its own `logs/AIRION-QA-<date>-<lane>-<area>.md` and its own published report.

**One lane also means one set of files.** Everything a session writes carries its lane, because two sessions sharing a path clobber each other mid-run: the session log `logs/AIRION-QA-<date>-<lane>-<area>.md`, the run `reports/runs/<date>-<lane>-<area>.md`, and — the easy one to miss — any driver snippet you create, which goes in `scripts/callrig/snip/` as `<lane>-<name>.mjs`. That last one bites hardest: snippet names like `night-toolbar.mjs` are generic, and a snippet silently rewritten by the session next door fails in ways that look like product defects. Shared, stable helpers (`lib.mjs`, `api.mjs`, `login.mjs`, `drive.mjs`) are read-only — never edit them mid-session, **and add new shared helpers in a new file rather than by extending a live one**. Even a purely additive change forces every running session to read the diff to satisfy itself nothing it imports has moved. **"Additive" is a promise about the API, not about behaviour**: widening what a helper matches can make a previously-failing call start succeeding, which silently changes the result of any measurement that depended on the old behaviour. Announce a behaviour change *before* it lands, so a session can finish what it is holding. `reports/README.md` is shared: append your row when you publish, not at the end of the run — it is one append either way, and a session that dies loses the row.

Alice owning `#qa-private` but not `#qa-general` exercises channel-permission differences inside a single account: her own message shows Delete + Pin in the channel she owns and only "Hide for me" in the one she doesn't.

**`qa.*.guest` holds workspace Member membership as well as `is_guest = true`.** `seed_qa_fixtures.py:139` is `WORKSPACE_MEMBERS = [k for k in UID if k != "qa_outsider"]`, so every fixture account except the outsider is a workspace member — the guest included, which gives it `workspace.<ws>.channel.create` among the Member role's permissions.

**Seeded fixtures are invisible to global search, and it looks exactly like a product bug.** `seed_qa_fixtures.py` writes straight to Postgres; the OpenSearch indices (`aloqa_channels`, `aloqa_users`) are fed by Kafka from the services (`search-service/internal/infrastructure/kafka/consumer.go`, `channel_upserted` → `IndexChannel`), and there is **no CDC on that path** — verified: the seeder contains zero kafka/opensearch references. So a seeded channel or account is never indexed and searching for one returns nothing. Messages and files are fine, because they were posted through the app. **Any "global search does not find X" finding against seeded data is measuring the fixture pipeline, not the product** — get a positive control by creating the thing through the UI first. Lane E carries a permanent one: channel `e-search-control`. The People bucket has no such control, because every fixture account is seeded; settling it needs a user registered through the app.

Staging also holds unrelated `qa.*` leftovers (`qa.probe.*`, `qa.livecall.*`) from older sessions — match fixtures by exact email or fixed id, never `LIKE 'qa.%'`.

## Start of a session

**First, fix your sector and lane.** A bare letter is the whole instruction: `/run-until 14:00 G` means **sector G on lane G** — read that sector's section in `SECTORS.md` for what to cover, and use the same letter for the lane. There are nine sectors, A-I, and each has its own lane. A prompt may still name them separately ("sector G on lane C"), and then they differ. Lanes run past the sectors — lane J carries no scope and is free for other work, so a letter with no sector is not an error. If the prompt names a lane but no sector, cover the sector of the same letter when one exists. If it names neither, you are sector A on lane A. If it names something that is not a letter ("lane 2"), read it positionally (2 → B) and write the reading at the top of your session log. A project hook (`scripts/hooks/sector_context.py`, registered in `.claude/settings.json`) normally injects the named sector's section along with its exact log and report filenames; if you did not receive it, read the file yourself. Then, before anything else: `export QA_LANE=<letter>` so every `d` call is guarded — **plus `export QA_SECTOR=<letter>` on the rare occasion sector and lane differ**, because `launch.sh` reads the sector off the lane letter otherwise and would hand out the wrong browser cap; `seed/seed.sh --verify --lanes <letter>` to confirm that lane's fixtures, and `node scripts/callrig/rigmap.mjs table <letter>` for your ports, profiles and sign-in emails. Launch any browser you need with `scripts/callrig/launch.sh <letter> <account>` and sign it in — a lane's browsers are yours alone; never drive a port outside your block. Every file you create carries the lane (see the fixtures section).

1. `seed/seed.sh --verify --lanes <your letter>` — confirms staging is reachable and your lane's fixtures are intact. Then `GET /api/v1/auth/me` in each browser to learn which account it holds (sessions persist between runs).
2. Record the deployed staging build — `curl -sL https://airion-cargo.store/ | grep -o 'data-dpl-id="[^"]*"'`. **`-L` is required**: the apex host answers 301 to `staging.airion-cargo.store`, so without it the grep returns empty, which reads exactly like a missing stamp. It is in the server HTML only; the attribute is gone from the hydrated DOM, so read it with curl, not from the browser. Put it at the top of the session log — a finding is only reproducible if you know which build produced it. No equivalent stamp found for the backend. The stamp names the frontend commit — see **Upstream** for how to read it.
3. Settings → Account → Language → English on every account you'll use.
4. `scripts/jira_cache.py sync` — mirrors every ALK ticket (all statuses and types, with descriptions) to `~/.cache/aloqa-qa/`. First run is a full fetch (~3.5 min, 35 paced pages); later runs top up by `updated >=` in about a second. Everything after that — `show`, `list`, `grep` — is local and free. Re-run `sync` once more before filing or writing the report: colleagues open tickets during a session, and the top-up costs a second. Comments are not mirrored, so reading a ticket's discussion is still a live call.
5. Create the session log `logs/AIRION-QA-<date>-<lane>-<area>.md` (lane letter and product area, e.g. `logs/AIRION-QA-2026-08-25-B-chat.md`) and log as you go — one `### BUG-N [Severity] [backend|frontend] title` block per finding, with the request/response or DOM measurement that proves it.
6. Keep a **`## Current state`** block at the top of that log — what is in flight, which hypotheses are open, what is measured but not yet written up. Refresh it as you go, not at the end: after compaction it is the first thing worth reading, and it is cheaper than re-reading the transcript.
7. Severity: **Critical** = a feature is unusable (500s); **High** = wrong data, security/privacy, or a control that can't be reached; **Medium** = broken UX with a workaround; **Low** = cosmetic, copy, i18n.

## Session conventions

### Reporting

- **Write the report in Russian**, keeping app labels, feature names, API paths, HTTP codes, CSS/DOM terms in English. Call out locale-specific bugs explicitly.
- **Label every finding `[backend]` or `[frontend]`** immediately after the severity in the heading — `### BUG-N [High] [backend] title` — based on where the defect lives (an API 500 is backend; a clipped label or unreachable control is frontend).
- The published report is bugs-only and written for developers who know nothing about the test setup — no account names, test call names, meeting/workspace/channel IDs, rig ports or fake-device labels. (The session log keeps full provenance, including verified-working notes.)
- **A finding is a file, not a section of a report.** Write `reports/findings/<id>.md`: flat frontmatter,
  then the sections below as `## ` headings. The `id` is the filename, and it is what a human's recorded
  verdict attaches to — so a title can be fixed later without discarding it. List the finding's id in a run
  (`reports/runs/<date>-<lane>-<area>.md`) to publish it, and render with
  `python3 scripts/render_report.py reports/runs/<run>.md`, which writes the HTML to `build/`.

  ```
  ---
  id: chat-failed-delete-silent
  title: Неудавшееся удаление показано как выполненное
  tags: FE-WEB, CHAT
  severity: High          # Critical | High | Medium | Low
  side: frontend          # frontend | backend
  surface: Chat           # routes the verification walk
  status: published       # published | withdrawn | duplicate
  lane: D
  accounts: alice, bob
  snippet: d-fail-delete.mjs
  build: v0.61.0-rc.7
  sha: 10a407a46be1
  ---
  ```

  Frontmatter is flat on purpose — scalars and comma lists, no nesting — so there is one shape to write and
  one to validate. `python3 scripts/verify_report.py` checks all of it.

- **A finding that turns out not to be a bug stays, as `status: withdrawn`, with a `## Почему снято` section
  carrying the measurement that killed it.** It never reaches a report, and it is the only thing that stops a
  later session re-discovering it and filing it as real. `python3 scripts/findings.py --withdrawn` lists them;
  read it before writing anything up.

- **Every finding ships a repro snippet, and its frontmatter names it.** The finding is verified by a human who
  must see the defect happen in a browser; the snippet is what removes the setup from that, not the judging.
  You already write one to find the defect — keep it, name it `<lane>-<short-name>.mjs`, and put it in
  `snippet:` with the accounts it drives.

  `scripts/callrig/snip/_repro-template.mjs` is the contract: get to the state, **prove you reached it**,
  then leave the human one action short of the defect and name that action. Return
  `{ready, asserted, stepsDone, leftToDo}` and call `progress(n)` as each of the finding's numbered steps
  completes — `progress` arrives in the snippet's argument object. `stepsDone` is how many of the
  *finding's* steps the script performed, counted from the first; the app ticks those off and highlights
  the next as the person's. The two must agree: claiming steps while emitting no `progress` leaves the
  list inert for the whole run, and a `stepsDone` below the highest marker makes a ticked step un-tick.
  Set `ready` false and say why when the state was not reached — **a snippet that lands someone on the
  wrong screen is worse than no snippet**, because that is how a verification passes while measuring
  nothing. Refusing is the contract working, not a failure.

  **Review** (`~/Applications/Review.app`, built by `macapp/build.sh`) is what a person uses:
  it presses the snippet, parks the browser beside itself, ticks the steps live, and records
  confirmed / not-a-bug into `verifications/verification-<date>.md` via File → Save Record. It carries **only findings
  whose snippet exists on disk** — no block means the finding is not in the app at all (`BENCH_ALL=1`
  overrides). `scripts/bench.py` is the same thing headless.

  It reads every run in `reports/runs/` and reloads when a source file changes, so a finding edited while
  the app is open appears on the next refresh without a restart. Pass `BENCH_TILE_LEFT` to change how much
  width the app keeps for itself.

  Judging is kept in `~/.cache/aloqa-qa/reproducer-state.json`, not in the reports: the verdict, any
  re-rated priority, and any rewritten «Ожидаемый результат». It saves itself as you work, survives a
  restart, and is never written back into the report HTML — Save Record is what turns it into a file.
  Changing one twice overwrites it, so the state is what you currently think, never a history.

  Two checks, and they answer different questions. `python3 scripts/check_repro.py` is static and
  instant: every block names a file that exists, honours the contract and carries its lane prefix.
  `python3 scripts/verify_snippets.py <lane>` actually runs each one against a live browser, driven by
  the account its own block names, and is the only thing that can tell you a snippet reaches the right
  screen.
- **Every finding follows one shape**, so a report entry becomes an ALK ticket without rewriting it:

  ```
  ### [FE-WEB][CALLS] Краткое описание проблемы

  #### Проблема
  Что делает пользователь, что происходит неправильно и чем это ему мешает. Два-три предложения.

  #### Как воспроизвести
  1. Первое необходимое действие.
  2. Действие, которое вызывает проблему.

  #### Фактический результат
  Кратко — что наблюдается.
  Измерение, доказывающее это (запрос и ответ, DOM), идёт сюда же отдельным блоком.

  #### Подтверждённая причина
  Подтверждённая техническая причина или узкая ответственная граница.

  #### Ожидаемый результат
  Кратко — что должно было произойти.

  #### Проверка
  - Основная regression-проверка.
  - Граничный или failure state.
  - Отсутствие регрессии в связанном рабочем сценарии.
  ```

  The report is HTML, so this is the structure, not the markup — headings, an ordered list, a `pre` for the
  measurement. Tag the title `[FE-WEB]` or `[BE]` then the module, matching the ALK summary style below.
  **A finding is not finished when the defect is proven, it is finished when someone else can arrive at the
  proof.** Reproducing twice, the citation check and the visibility check all verify the first half; these two
  verify the second. **Everything visible in the measurement block must be produced by the steps above it**, and
  the « must not break » lines must be true today. The block is pasted from what you actually did; the steps are
  written from what you think matters, so they drift. One report's block showed a `custom_status.text` value its own
  repro steps never told the reader to set — and that field was the *control* proving the
  surface can render anything at all, so a developer following the steps would have seen a
  weaker finding than the one measured.
  **Фактический результат** is what you saw, not why. One or two sentences, then a single block carrying the
  request and the response that proves it — the reader should reach the proof at a glance. **Paste the
  response as it came back**: real field names, real status, trimmed to the part that matters, with ids,
  emails and tokens replaced by placeholders. A hand-written summary of a response is a second chance to
  get it wrong, and a report had exactly that corrected on re-verification. Where several cases differ,
  show each actual body rather than tabulating what you concluded from them. Reasoning
  about what the response implies belongs in **Подтверждённая причина**, not here; a screen transcript earns a place
  only when the wording itself is the defect. Several stacked blocks with interpretation between them is the shape
  to avoid: it buries the one measurement that matters.
  **A refutation is finished when you find where the behaviour is correct, not when you fail to reproduce it.**
  "We could not see it" invites the reply that you looked wrong; "here is the state where it legitimately renders,
  and here is the condition that excludes it everywhere else" cannot be answered that way. One cross-sector flag —
  generic channel-onboarding copy appearing on a personal notes page — was killed properly only by creating a brand
  new empty channel and finding the copy *visible* there: the shared layer is the onboarding state of a new channel
  and is faded to `opacity: 0` everywhere it does not apply. That turns "an `innerText` artifact" into "a correctly
  conditioned template", which is a different and much stronger claim.
  **For any finding of the form "surface S fails to do X", run X's neighbours on S before you
  describe the scope.** A positive control proves the defect is real; the neighbouring actions
  prove where its *edge* is, and the edge is what a developer acts on. One finding began as
  "the thread panel does not apply realtime updates" — the deleted reply stayed visible for 33 s
  across 22 samples while the same request's channel message was marked deleted on the first
  sample. Editing that reply and reacting to it both landed in the open panel on the first
  sample, 1.5 s. So the panel receives and applies realtime perfectly, and the true finding is
  one event on one surface. The wide version sends a developer to the panel's subscription; the
  narrow one sends them to the delete handler. Same measurement, different afternoon.
  **A finding of the form "X does nothing" needs a state where X demonstrably does something —
  without one you cannot separate an inert feature from one whose precondition you never met.**
  This is the positive control as a *correctness* requirement rather than an evidential one, and
  it catches a failure no other check here does. One published finding said a search filter did
  nothing. The measurement was correct — results identical to unfiltered — and the conclusion was
  wrong: the filter scopes to the DM with that person, and no DM existed yet. The two are
  **indistinguishable until a DM exists**, and three verification passes re-ran it and confirmed it
  every time, because the state never changed back. Reproducing twice cannot catch this; reading
  the code path cannot either.
  **The question to ask of any measurement: can it distinguish the hypothesis from its opposite —
  what would a *working* version have produced, and is that different from what I saw?**
    **For any finding of the form "the app fails to do X", find somewhere the same app does X
  correctly, and put it in the finding.** It costs one measurement and removes the reviewer's
  best objection. A negative alone is compatible with "your setup was wrong" — and that
  objection has been right twice in one day, once against a broken fixture and once against
  an actor whose role had silently changed. A positive from the *same* screen, session and
  account closes it. Worked examples: the same `audit.view` action granted at workspace layer
  opens the section completely while the company-layer grant does not, which rules out "the
  section is broken", "the wildcard is ignored" and "your role was wrong" at once; a duplicate
  role name produces its own specific message, proving the client *does* map server error keys
  to copy and simply has none for the key in question.
  **Подтверждённая причина** means confirmed, and the word is load-bearing. Two things qualify: a cause read
  out of the source with a file-and-line citation the reader can open (`git grep` the i18n key or the endpoint,
  then name the file). **Verify every citation exists before publishing** — one line per path, `git cat-file -e "<deployed-sha>:<path>" && echo EXISTS || echo ABSENT` — and write full paths, not fragments relative to a base stated elsewhere, so the reader can paste one straight into `git show`. A citation is the one claim in a report nobody re-measures: findings get re-verified, the file-and-line beside them looks like metadata, and it is what the developer acts on first. Note the check proves only that the reader arrives somewhere: not the line numbers, and not that what they find there shows the defect. Open each cited range and ask whether a developer reading exactly those lines would see what you claimed — citing the table an enum lives in, rather than the code that mishandles it, passes every mechanical check and shows the reader nothing. Or a **narrow responsible boundary** a measurement already proves — "the response arrives
  without the field, so nothing in the client dropped it" puts it on the backend without claiming to know why.
  A mechanism you inferred from behaviour is neither. **Omit the section rather than fill it**: a wrong cause
  costs a developer more than an absent one, and it is how a finding reaches the wrong team. Keep it to a
  sentence or two; it sits outside the word budget, like the measurement block.
  **Classify your causes before auditing them — only one class can be wrong in a way testing cannot catch.**
  A *boundary* cause says where the defect is **not** ("the response arrives without the field, so nothing in
  the client dropped it"); the measurement already proves it. An *omitted* cause carries no risk. A *mechanism*
  cause asserts how the defect happens, and **re-running the repro cannot falsify it** — one published cause was
  self-refuting on its own citation, survived three verification passes, and was found only by an unrelated probe.
  Every pass re-checked the behaviour; none re-checked the reasoning.
  **The specific trap: do not describe the wire response as though it were what the component receives.** An
  adapter sits between them — it can construct fields the wire never sent, hardcode values, and drop others
  entirely. A claim of the form "the client sees X" measured with a console `fetch` has that gap unless you have
  read the adapter, and it points a developer at the wrong file. Read the path from wire to component, or state
  a boundary instead.
  **A guard nobody has watched fail is a guard nobody has tested.** Before trusting any checker, guard or
  verification step, reconstruct the failure it exists for and confirm it actually fires — a checker that has
  only ever passed is the same defect as a measurement that cannot distinguish its hypothesis from the opposite.
  The session that wrote `scripts/verify_report.py` rebuilt the exact bug that had destroyed one of their
  findings, ran it, and watched three independent checks trip; that is what makes `ALL CHECKS PASS` mean
  something on the good file.
  **Run the « must not break » lines against the live build before publishing.** They are the only part of a
  finding that makes a claim about code you are **not** reporting on, and nothing else in this process ever checks
  them — they are written from expectation, published, and read months later by someone who assumes you verified
  them. **A guard that is already false is worse than no guard**: a developer runs it after their fix, sees a
  failure they did not cause, and either chases it or stops trusting the list. Running them also sharpens findings.
  One sector's guard established that the string in question is correct and visible on an owner's own unshared
  file — so the defect was not the copy but showing an empty state in a non-empty one, which decided between two
  candidate fixes the finding had offered. Where a guard has a known trap, say so in the line: after a *decline*
  a meeting leaves the grid immediately, so the persistence check is testable with Yes and someone trying No will
  find the chip gone and read it as a second bug.
  **Проверка** is what a developer runs to confirm their fix, not what you ran to find the bug — three lines is
  usually right. UI labels stay in **English** (the app is used in English) inside the Russian prose. Plain human
  wording — not "no-op", "accessible name", "оверлей". Severity lives in Jira's Priority field, not in the
  description text.
- **Keep each finding short — a developer reads it, not a jury.** Four things earn their place: what breaks, in one or two sentences; the click path; the measurement that proves it; and the «Как должно быть» block. Around 120–180 words of prose is plenty. **Treat the budget as a structural check, not a
  style check** — run it mechanically and look at what pushed a finding over rather than
  trimming. In one audited report every overrun was a *placement* error, never wordiness:
  a positive control had drifted into **Фактический результат** instead of the triage note.
  Nothing needed cutting; something needed moving, and reading it would not have found that. That budget covers the explanatory prose only — **Проблема**, **Фактический результат** and **Ожидаемый результат**. The click path, the measurement block, **Подтверждённая причина** and **Проверка** sit outside it, and none of them should ever be squeezed to hit the number: steps are what make a finding reproducible and Проверка is what makes a fix verifiable. Never move prose into a code block to escape the count — a measurement block holds measurements, and the test for anything you put there is whether it would still belong if there were no budget at all. Cut argumentation that the finding is real, the same fact restated in different words, and speculation about what a user would think or conclude. One sentence ruling out the obvious dismissal — wrong account, empty state, stale client, environment drift — earns its place; a paragraph of it does not. A finding a developer can act on after one read is finished; one that persuades is too long.
- **When you suppress a finding as a duplicate, log it in full with the ticket key.** Widening the dedup surface has a cost that only shows up later: a finding suppressed against a ticket nobody works is a finding nobody sees, and the suppression leaves no trace to recover it from. The ticket you deduped against may also carry less than you measured — one BLOCKED bug matched a finding exactly and consisted of a title and nothing else, so treating it as the duplicate would have replaced steps, a measurement and a verification section with a bare summary. Keep the full finding, the key, and what your version has that the ticket does not.
- **A satisfied requirement looks identical to a break — the measurement being right is not the same as the finding being right.** One sector nearly filed "unknown audit actions render raw" against a ticket specifying exactly that, and "the dead-link page has zero controls" against a ticket whose criteria read *fail-fast without the form*. Both measurements were correct; both described a state the product was built to produce. Before calling a measured state a defect, check whether some ticket **specifies** it — and if one does, the finding is not dead, it is narrower: that ticket owns only what its criteria enumerate.
- **An adjacent ticket owns the states its acceptance criteria enumerate, not the whole mechanism.** When deciding whether an open ticket already covers your finding, read its **Проверка** rather than its **Проблема** — two findings can share a code path and have disjoint acceptance criteria, and a developer closing that ticket to its own checklist would never touch yours. It makes the call in about a minute, and it is a genuine discriminator rather than a way to keep everything: the same test let one sector **keep** findings that two nearby tickets appeared to own, and **stopped** a third from being framed as a defect when the ticket's criteria specified exactly the state measured. Same rule, opposite outcomes.
- **Don't suppress unilaterally where the rule doesn't reach.** The dedup rule names its statuses and issue types; a ticket outside them is an adjacent open item for the log, not an instruction to delete measured work mid-run. Widening the rule changes what every sector reports and is the user's call.
- **A report already published for your sector is a dedup target, and a closer one than Jira.** We never file without being asked, so `reports/` is where findings actually live and ALK holds only the subset someone later chose to file — an unfiled finding is invisible to the Jira dedup permanently. Check the **source directory**, not `reports/README.md`: the index is appended once at the end of a run by design, so mid-run it is guaranteed incomplete and reads exactly like "no sibling exists". `grep -h '^title:' reports/findings/*.md` lists every finding ever written, published or not, which is a wider and cheaper net than any report was. **Match on the titles, never on the lane letter** — a letter says which fixtures produced a finding, not what is inside it. **Reading a document is not checking a claim against it** — a session that had read the sibling, re-verified all five of its findings and quoted the colliding one twice still published the duplicate, because it sat in memory as context rather than as a dedup target. It needs its own pass.
- A finding that gets withdrawn stays in the session log with the reason and the measurement that killed it — otherwise a later session re-discovers it and files it again. **So look for those before you publish**: `grep -il 'ложн\|false positive\|отозв' logs/*.md reports/README.md`, and read what the hits name for your area. A recheck run's README row lists exactly what it killed, which is far cheaper than rediscovering one. Anything the dedup pass turns up that is not your finding — an adjacent open ticket on the same screen, a candidate to merge with — goes in the session log, not the report: the report is bugs-only.
- The app is in active development — cosmetic trivia gets trimmed at triage rather than filed. This filters what gets **written up**, not what gets **tested**: keep probing everything and keep every finding in the session log, then decide which ones earn a place in the report or an ALK ticket.
- **Dedup against Jira before reporting.** Don't file or report anything already open in project **ALK** as `issuetype = Bug` with `status IN ("Backlog","Ready","In Progress")`. **`TESTING` means the ticket is closed** in this project's workflow — it is not a queue awaiting QA, and tickets in it are not duplicates to dedup against. `jira_cache.py list --open-bugs` applies exactly this filter.
- **`list --open-bugs` is the dedup scope, not the whole mirror — it hides the statuses where a *specified* state lives.** TESTING is closed and BLOCKED is outside the rule, so neither appears, and both are where a ticket that makes your measured state deliberate will be. Before writing a finding up, also run `jira_cache.py grep '<the noun of your finding>'`, which searches summaries and descriptions across every status. Reading the open list is not this step.
- Dedup by reading, not searching: `jira_cache.py list --open-bugs` and read every summary, then `jira_cache.py show <KEY>` for the full description of anything even loosely related. Titles and descriptions diverge often enough that keyword and stem matching misses real duplicates; `grep` is for spot-checks only. All of it reads the local mirror.
- **The summary table, the severity chips and the spelled-out count are generated from one list, so they cannot disagree with the articles.** That used to be the most expensive failure available here — a find-and-replace overwrote a published High with a duplicate of another finding and every count-based check passed for over an hour, because a substitution changes no count; separately a table was severity-ordered while the articles were not, ten of fifteen positions disagreeing with seven checks green. Neither is reachable now, which is why `verify_report.py` no longer looks for them. What it does check is the content: `python3 scripts/verify_report.py` for every finding and run, and `python3 scripts/verify_report_selftest.py` to confirm each of its checks still fires — twenty-five mutations, each asserted to be caught **by its own check**, because three of them were first caught by the wrong one.
- **An isolation claim has to trace the execution path, not the import graph.** "Zero of my 554 snippets import that file" answers the wrong question: `drive.mjs` imports `HOOK` from `lib.mjs` and injects it with `addInitScript` before every snippet, so shared code is on every run's path regardless of what any snippet imports. Injected init scripts, wrappers, and anything a runner pulls in on your behalf are all invisible to "what do my files import". Then, having established what is on the path, ask what changed in it:
- **To answer "did this edit change what I depend on", read the hunk headers, not the exports.** `git diff -U0 <file> | grep '^@@'` — every hunk showing `-N,0` consumes zero old lines, so the change is a pure insertion and nothing existing moved. Plainer still: `new.startswith(old.rstrip('\n'))`. Both answer it without knowing where any export begins or ends. **Slicing from one `export const` to the next breaks precisely when a neighbour is appended** — the last export's slice used to run to EOF and now stops at the new one, so it reports CHANGED when nothing did. That false alarm points the *safe* way, which is why it would not have looked wrong: it would have sent four sectors to re-run clean work. Note also that a hunk header names the nearest declaration **above** the insertion point, not the scope the change landed in.
- **`[x for x in items if 'substring' in x][0]` is not a selector.** It picked the wrong article twice in one session, once destroying a finding — the matched phrase also appeared in a different finding's body, and `[0]` took document order. Address a finding by its `id`, which is its filename, and assert **exactly one** match before editing anything selected by content. The same failure has a file-level twin: an edit idiom that opens for writing before reading truncates the file it was meant to modify. Both fail silently, and both were caught by accident rather than by a check.
- Before publishing, grep the report for test-setup traces (account names, `qa.*@aloqa.test`, user/meeting/channel/workspace ids, rig ports, fake-device labels, staging host, test call names). They leak most easily inside pasted measurement blocks. **Scrubbing is editing the evidence, so re-read every block you touched.** Substituting a placeholder is the one moment a report acquires text that was never measured, and the result looks exactly like a real measurement: one report ended up quoting a marker from a different run, whose message had been sent by API and therefore could not have exhibited the escaping the finding was about. The block was internally impossible and still passed review. After scrubbing, check each block against the run it came from, not just against the redaction list.
- **Never create ALK issues or post comments without being asked.** Log findings and put them in the report; filing is a separate decision the user makes.
- Jira is reached over the REST API with a **personal API token** — `QA_JIRA_SITE` / `QA_JIRA_EMAIL` / `QA_JIRA_TOKEN` in `seed/.env.local`, all calls via `scripts/jira_api.py`. A personal token is subject only to Atlassian's `"jira-burst-based";q=100;w=1` (100 req/s, no app quota), so throttling is not a practical concern. `scripts/jira_token_check.sh` confirms auth and prints the live quota without revealing anything. Create or rotate a token at https://id.atlassian.com/manage-profile/security/api-tokens.
- ALK ticket summaries are written in Russian with bracket tags, e.g. `[FE-WEB][CALLS][SIDE ROOMS] …` — match that style if filing.
- **Filing and commenting go through `scripts/jira.py`**: `jira.py comment KEY --file body.md`, `jira.py create --summary '…' --file body.md --priority High --labels frontend`, plus `search`/`get` for one-off reads that the mirror does not cover (comments, for instance). Bodies are written in Markdown and converted to ADF (headings, paragraphs, fenced code with language, bullet/numbered lists, tables, `**bold**`, `` `code` ``). Reads write the payload to a file so it never enters context.

### Browser tooling

- Run **as many browsers as the scenario needs** — one per account is fine, and there are 8 fixture accounts per lane. A session lives in the browser's cookie jar, not the tab, so each account needs its own browser or profile — a 3-way test is three separate windows, not three tabs.
- Network/CPU shaping goes through Playwright CDP: `ctx.newCDPSession(page)`, then `Emulation.setCPUThrottlingRate` for the renderer and `Network.emulateNetworkConditions` for the network (next bullet for what the latter does not touch). There is no plugin for this — no emulate presets, no performance traces, no `lighthouse_audit`; drive CDP directly.
- CDP `Network.emulateNetworkConditions {offline:true}` blocks the page's HTTP but **not** WebRTC media — media keeps flowing, so a survived "outage" is not evidence of network resilience. `Emulation.setCPUThrottlingRate` does affect the renderer.
- Viewports: test at desktop widths. Mobile and narrower-than-desktop windows are out of scope, and layout findings that only appear below desktop width are not written up.
- Know each browser's throttling: Playwright MCP (`mcp__playwright__*`) has been visible and unthrottled; the Claude Browser pane (`mcp__Claude_Browser__*`) was usually `visibilityState: hidden` with timers throttled to 1/s. A "slow channel load" false positive came from timing in that hidden pane — `document.visibilityState` is worth checking before trusting any timing. **Record `visibilityState` in every sample of a cross-window live-UI measurement**, not just once: a rig window occluded by another rig window reports `hidden`, and the app suppresses live UI such as the typing indicator when it is. `document.hasFocus()` does not detect this — it stays `true` in both states.
- Playwright selectors: prefer `button[aria-label="…"]` and `data-testid` (e.g. `call-end-confirm-submit`); `text=`/`has-text` selectors routinely match two elements (strict-mode error) or hit sidebar headers — scope to `main`. Match `aria-label` exactly, not by substring: sibling controls share vocabulary, so a loose regex silently clicks the wrong one and the product looks broken.
- `browser_file_upload` accepts files only from inside this repo (allowed roots: this directory and `.playwright-mcp/`) and fires only after clicking "Browse"; targeting the hidden `<input type=file>` did not work.
- `browser_network_request` takes the 1-based `index` from `browser_network_requests`, not an id.
- Calendar event chips (`button[data-testid="calendar-event-chip"]`) for later-in-the-day meetings sit below the fold: the locator finds them but the click never lands and no dialog opens. `scrollIntoViewIfNeeded()` first — a chip that "does nothing" is usually off-screen, not broken.
- **State each selector separately; a block that collapses several into one `== 0` is fragile in a way a per-selector block is not.** The union hides which member you actually verified, and any incidental accessibility node breaks the claim without touching the defect. One report asserted `button | a[href] | [tabindex] == 0`; re-measured it was 1 — a zero-height `SECTION tabindex="-1"` live region, out of the tab order, with the finding entirely unaffected. A developer re-running that line gets 1 and doubts the finding rather than the count.
- **Rebuild a repro from the finding's steps, never from its title.** Two wrong-screen tests in one pass came from reconstructing off the title, and the dangerous shape is the second: a wrong call id renders a "Call has ended" page **with** a `Back to workspace` button, so a published finding reads as failing to reproduce. That is the most expensive false alarm available and reading the steps costs one grep.
- **An enumeration over a bounded set is safe; a search over an unbounded one is only as good as the bound you did not state.** Requests a screen makes, controls in a container, entries in a catalogue — bounded, and a claim about them cannot be broken by where you stopped reading. Page text, response bodies, DOM matches — unbounded unless you say where you cut. That is why "the card makes exactly these three requests" survives scrutiny that "the text does not contain X" does not, and it is the principle underneath every truncation failure here.
- **Cap the capture, not the display.** These two pull opposite ways — keep return values small, but never truncate a list you are about to make a claim about — and the resolution is *where* the limit goes. A capture you capped is a capture you know is capped; a full capture printed as `x[:6]` is indistinguishable from a null result. One session's 30-second watcher **did** record the error it was looking for, and the sentence sorted past position six in the print statement — the window was right, the DOM was right, and the finding was wrong. Reduce inside the page (count, filter, match) and return the reduction, rather than returning everything and slicing it on the way out.
- Keep `browser_evaluate` return values small (slice strings, never return element lists) — large results get dumped to a file and truncated.
- Measure layout defects, don't eyeball them: clipping = `scrollWidth > clientWidth` on a visible leaf **wider than ~24px**, **and `text-overflow` is not `ellipsis`**. Both guards are needed. Deliberate truncation satisfies the width test and is not a defect; and screen-reader-only labels are 1px boxes holding real text, so they satisfy it *by construction* — without the width guard every screen reports clipping, and the test gets distrusted rather than fixed. Skip `sr-only` classes and absolutely-positioned elements ≤1px wide too; unreachable controls = `getBoundingClientRect().left >= innerWidth` with `documentElement.scrollWidth === innerWidth` — **the horizontal test only; there is no valid vertical analogue.** `top >= innerHeight` flags every row below the fold, which is normal scrolling, not unreachability, and it has no companion condition to rule that out (a page is *supposed* to be taller than the viewport). Extending it vertically flagged ten ordinary hub rows; thread/pinned counts via the API.
- **A hit test answers "is this on screen now", never "does this exist and can I drive it".** `vis()` rejects an element that is `display:block` and visible by every CSS test but sits below a scrollable dialog's fold, because `elementFromPoint` returns whatever is scrolled over it — so a present, drivable control reads as absent or inert, which is indistinguishable from a real defect. The tell is a contradiction inside one measurement: the dialog's `innerText` contains the string while no *visible* element does. `scrollIntoView({block:'center'})` first, then re-measure; `safeClick()` already does this, a bare `vis()` does not. Same family as needing `boxVis()` for containers.
- Visibility needs the ancestor chain, not one node: `display`/`visibility`/rect miss a parent with `opacity:0` or a zero-height `overflow:hidden` wrapper, and a clipped child still reports a non-zero rect at a plausible `y`. Check the `opacity` product up the ancestors plus `document.elementFromPoint()` at the element's own centre — `scripts/callrig/snip/b-visible.mjs` does both.
- The published artifact URL needs a claude.ai login (Playwright sees a 404). To eyeball the HTML, wrap it in `<!doctype html><html><body>…` in a temp folder and serve with `python3 -m http.server`; delete the folder after.
- Session clock: `TZ=Asia/Tashkent date '+%Y-%m-%d %H:%M:%S %Z'` — the app and the team run on +05.

### Call testing rig (`scripts/callrig/`)

- `scripts/callrig/launch.sh <lane> <account>` (e.g. `launch.sh B alice`) — one Chrome for Testing per account with `--use-fake-device/ui-for-media-stream`, started maximized, profile at `~/.cache/aloqa-callrig/<profile>`; drop `audio.wav` / `video.y4m` in that dir for per-user distinguishable media. **`QA_FAKE_CAMERAS=2 ./launch.sh <lane> <account>` gives that window two selectable fake cameras instead of one**, which is what makes camera *switching* reachable; the host's own camera is not a route in, because the fake-device flag replaces real devices rather than adding to them. It is opt-in because a fake video *file* collapses enumeration back to one device whatever the count says, so that window trades its per-user video feed for the second camera. The Chrome path is hardcoded to a Playwright cache build — update `CH` if that build is gone.
- **`--use-fake-device-for-media-stream` fakes the *screen* as well as the camera and mic.** `getDisplayMedia` under the rig flags does not touch the real display: it returns Chrome's synthetic capture source — a flat green field with a rotating pie slice, corner squares and a live timestamp, at the display's resolution scaled by 1.33. That is a real, animated, distinguishable video source, so "the sharer shares and the viewer sees it" is testable exactly as it stands. What is **not** testable is source *selection* — sharing a particular window or a second display — because there is only ever the one synthetic source behind `--auto-select-desktop-capture-source`.
- **Real screen capture cannot be enabled on this binary, and granting Screen Recording will not do it.** The Playwright Chromium build is **ad-hoc signed** (`codesign -dv` reports `Signature=adhoc`, `TeamIdentifier=not set`), so TCC has no stable code identity to bind a grant to: the grant is accepted and stored, and `getDisplayMedia` still fails `NotReadableError: Could not start video source` once the fake-device flag is removed — measured both by direct exec and via `open -g -a`, which attribute to different TCC identities and fail alike. Note the two identities, because they make the database confusing to read: microphone is recorded against the **executable path**, screen capture against the **bundle id** `com.google.chrome.for.testing`, so a query matching one form misses the other.
- **Judge a capture by looking at the frame, not by its statistics.** Summary numbers over a captured frame — colour count, luminance spread — cannot tell Chrome's synthetic source from a real desktop that happens to be flat, and a low spread reads as "something is wrong with the capture" when nothing is. Write the frame to a PNG and open it; the synthetic source is unmistakable on sight and ambiguous in every aggregate.
- **A launch starts clean and in the background.** Rig browsers get killed rather than closed, so Chrome keeps a restorable session and would reopen the previous run's tabs alongside the one `launch.sh` opens; the script deletes `Default/Sessions` and the `Current`/`Last Session|Tabs` files first, which leaves cookies and logins intact. It also starts Chrome through `open -g`, so a launch never takes focus from whatever the user is doing. `open` makes macOS treat Chrome for Testing as its own application rather than letting it inherit the launching process's permissions, so it asks for microphone, local network and the like on its own account — answer such a dialog once, and never click through one from a snippet.
- **Shell traps that produce confident wrong answers when driving the rig**: a heredoc quoted as `<<EOF` rather than `<<'EOF'` lets the shell eat `${...}` before python sees it; an over-escaped regex matches nothing and reports zero; `cd` into the source clones leaves the working directory there for the next call (`scripts/callrig/d` exists because of this); and `/dev/tcp` reports a browser down that is up — `curl …/json/version` is the reliable check.
- **Playwright cannot close a page whose renderer is gone** — a crashed tab needs `curl http://127.0.0.1:<port>/json/close/<targetId>`. Worth knowing before a long soak leaves dead tabs behind, and worth checking CDP targets before writing off a hung run: one such run turned out to be carrying a usable measurement.
- `snip/tabs.mjs` reports a browser's tabs with their navigation-entry counts. `QA_CLOSE_TABS=1` closes tabs opened and never driven; `QA_CLOSE_TABS=all` collapses a window to the tab carrying the most history. Both are deliberate, invoked calls — the app parks a window on the workspace default home after Cancel request, Back to workspace or a declined invite, and a discarded tab reloads with a fresh one-entry history, so neither the route nor the entry count proves a tab is idle.
- `./ensure.sh <lane> <account>...` — brings a lane's browsers up and signed in, repairing only what is missing. A browser already signed in as the right account is left completely alone: it reads the session via `snip/whoami.mjs` without navigating, unlike `login.mjs`, which goes to `/login` before it checks. Idempotent and safe mid-session, so it is the first thing to run after losing a browser unexpectedly.
- `./stop.sh <lane> [account...]` — closes browsers by profile directory (never reaching into another lane) and appends every closure to `~/.cache/aloqa-callrig/rig-events.log`. **A browser killed from outside is indistinguishable from a product crash seen from inside a snippet** — a dead port surfaces as `Page crashed`, `ECONNREFUSED`, or `Target page, context or browser has been closed`, exactly like a real defect. Read that log before believing one. The other tell is that windows you were *not* driving died too, including ones running nothing.
- `snip/lib.mjs` exports shared measurement helpers. Install the in-page half with `await page.evaluate(DOM)`, then call through `window.__qa`: **`vis()` for leaf controls** (hit-tests its own centre) and **`boxVis()` for containers** (deliberately does not — a `[role=dialog]` fails a hit test at its centre because its own backdrop is on top, so one helper for both reports open modals as absent); `clickDeepest()`, which matches `aria-label` as well as text and picks the candidate containing no other candidate, so an `<LI><BUTTON>` row resolves to the button instead of swallowing the click silently; `popperPick()`; `notices()`. Node-side: `safeClick()` scrolls, **re-reads the box** and proves the element is topmost before clicking — reporting `off-viewport` (the scroll did not take: a rig problem) separately from `covered` (something is on top: possibly a real finding), because collapsing the two is how the wrong bug gets filed; `waitClick()` returns the elapsed time at which a control appeared, which is often the measurement itself; `watchNotices()` implements the toast recipe.
- `snip/leave-call.mjs` leaves a call *and* ends the meeting — leaving alone keeps it `active`, and every navigation then bounces the tab back to `/call/<id>`. `snip/switch-account.mjs` signs a browser in as a different account in place; `snip/whoami.mjs` asks a browser who it currently holds, without navigating.
- `snip/watch.mjs` — `waitForChange(page, {selector|predicate, timeoutMs})` polls until a state changes and **returns "it never changed" as a result, not an exception**: `{changed:false, stableForMs, samples}` is what a "this state never resolves" finding is made of, and a thrown timeout reads like a broken snippet instead. It samples the whole document (a row can live in a portalled dialog) and strips volatile text — durations, `Nms`, "running N min" — before comparing, because a ticking duration badge otherwise reports dozens of changes and buries the real transition.
- `scripts/permission_matrix.py [sha]` — a worklist of single-permission probes for the admin area, ordered by disagreement, not a permissions × screens grid. It joins what each endpoint documents (`openapi.json`) against what the frontend gate actually asks (`deriveAdminCapabilities`), both read at the deployed sha, and emits `gate-narrower` (the backend would allow it, the gate never asks about that layer), `gate-silent`, and the actions no operation documents. Each row carries the probe verbatim. Resolves the deployed sha itself if you do not pass one.
- `scripts/callrig/SELECTORS.md` holds testids, menu shapes and selector traps — lookup data that drifts with the product, which is why it is there and not here. Check it before hand-rolling a selector, and correct it when you find it wrong.
- **Re-signing a window to another account of the same lane is legitimate.** It is how you reach a fifth account while at the per-lane window cap, and the only way to have one account signed in twice at once. The lane guard compares the lane of the signed-in email, not the account-to-port mapping, so it allows this by design. `rigmap.mjs email` then no longer describes that port — record the swap in the session log, and use `snip/whoami.mjs` to ask a browser who it actually holds.
- **One window per participant, not tabs of one window.** Guest sessions share the browser's cookie jar and occupy 3 slots (`GUEST_COOKIE_MAX_LIVE`, see ALK-2721) — a 4th guest in the same window evicts the oldest, and the resulting reconnects look exactly like application defects. `launch.sh` gives each participant its own profile and window.
- **Testing sessions never commit. The supervisor commits, after every change.** Parallel sessions committing concurrently to shared files — `CLAUDE.md`, `PITFALLS.md`, `reports/README.md` — would conflict and could destroy each other's work. Sectors append to the shared files and write their own logs, reports and snippets; the supervisor commits all of it as it lands. Untracked work has no safety net: a bad edit truncated a 1050-line handover file to 30 lines, recoverable only because every write to it happened to be in the session transcript.
- **Per-lane browser caps come from the accounts a sector's scope actually needs**, not from the worst single finding: no one finding needs more than three, but browsers accumulate as you work down a lane, so the cap has to cover the distinct accounts it touches. `launch.sh` prints the cap and the `QA_MAX_PER_LANE` override when it refuses. **Every sector may hold four**, which with three sessions running at once means any three together want twelve windows against a global cap of twenty — a ceiling rather than a budget that has to sum to anything. Four is not a target: a browser you are not driving is one the machine is still compositing, and `SECTORS.md`'s per-sector `Setup` line says what a sector actually needs.
- **A snippet is bound to its lane.** It hardcodes its own workspace id and names its own lane when it reaches for a second browser, and the bench drives it on the lane the finding names — that is consistent, not a defect. The one hazard is that such a reach calls `connectOverCDP` directly, where `drive.mjs`'s guard cannot see it, so `rigPort` refuses when `QA_LANE` names a different lane rather than quietly driving another session's window.
- **One browser block per lane, so parallel sessions can't collide.** `scripts/callrig/rigmap.mjs` maps `(lane, account)` to a CDP port, a profile and an email: lane A owns 9220–9229 with its original profile names, lane B 9230–9239 as `b-alice` …, and so on. `launch.sh` caps how many browsers one lane may have up at once and how many run across all lanes — it prints the cap and the exact override (`QA_MAX_PER_LANE`, `QA_MAX_BROWSERS`) when it refuses, so going past one is deliberate rather than accidental. It also refuses to start on a port that is already listening, and waits for a CDP **page** target before returning — a fresh Chrome reports zero targets for a few seconds, Playwright cannot attach to a browser with no page, and a non-page target does not count. If none appears it refuses rather than handing back a port that cannot be driven; raise the wait with `QA_LAUNCH_TIMEOUT` (seconds) when the machine is loaded. Query it directly with `node rigmap.mjs table B`.
- **Address browsers by lane and guard every call.** `./d b:alice snip/x.mjs` resolves the port itself; a bare port still works. Export `QA_LANE=B` once per session and `d` refuses to drive any browser outside that lane — by port block, and by the account it is signed in as.
- `node scripts/callrig/drive.mjs <port|lane:account> snip/<name>.mjs` connects over CDP and runs a snippet exporting `default async ({page, ctx, browser, pages})`; it prints the return value, so keep it JSON-serializable and small.
- `scripts/callrig/d <port|lane:account> snip/<name>.mjs` — wrapper that cd's first; the Bash tool's working directory resets between calls, so bare `node drive.mjs` fails intermittently.
- `snip/lib.mjs` exports `HOOK` (auto-injected — `window.__pcs`, `__gumCalls`, `__gdmCalls`), `RTC_STATS`, `UI_STATE`; ready-made snippets sit in `snip/`.
- `RTC_STATS` collapses simulcast layers — it can report 0 outbound video for a participant who is streaming fine on a lower layer. Confirm from the *receiving* side (`framesDecoded` rising) before concluding media has stopped.
- Prove media actually flows with `RTCPeerConnection.getStats()` (`bytesSent`, `framesDecoded`, `audioLevel`, `totalAudioEnergy`) rather than from the tiles on screen.
- Have a snippet clear the composer before typing into it: text left by an earlier snippet merges into the next message and reads as an input defect. **The usual way of clearing it does not work here** — `Control+A` is the emacs "move to beginning of line" binding in macOS Chrome, so `Control+A` + `Backspace` leaves the composer populated and the next `type()` inserts in front of the leftover. Use `Meta+A` + `Delete`, verify emptiness in a loop (Lexical restores drafts asynchronously after a reload), and discard the measurement if it never empties.

## Staging infrastructure

Credentials for Postgres, Redis, MinIO, SigNoz and SSH live in **`seed/.env.local`** — gitignored, never committed (this repo's GitHub remote is public). `seed/seed.sh` sources it automatically; `cat seed/.env.local` when you need a value by hand. If it is missing, `.claude.local.md` documents the keys it must define.

- A user only works if it exists in **all five** databases that hold user rows. `auth_db` is the identity of record (`password_hash`, `email_verified`); `org_db` owns companies/workspaces/channels/roles/memberships; `messaging_db`, `notification_db` and `realtime_db` keep replicas. `file_db` and `gateway_db` have none.
- Passwords are **bcrypt `$2a$`, cost 10**. Go's bcrypt rejects `htpasswd`'s `$2y$` — mint hashes with python `bcrypt.gensalt(rounds=10, prefix=b'2a')`.
- System `pip3 install` is refused (PEP-668, externally-managed). Use a venv — `seed/seed.sh` already provisions one.
- IDs are `generate_slack_id(prefix)` = prefix + 14 base36 chars: `U` user, `O` company, `W` workspace/workspace_member, `C` channel, `R` role, `K` company_member, `P` channel_member & role_permission. Membership tables all have `(scope, user)` unique keys, which is what makes the seed idempotent.
- `psql`: source `seed/.env.local`, then **`export PGPASSWORD="$QA_PGPASS"`** — psql does not read `QA_PGPASS` and will sit on an interactive prompt without it. Then `psql "host=$QA_PGHOST port=$QA_PGPORT user=$QA_PGUSER dbname=<db> sslmode=require"` (**sslmode=require** is mandatory).

## How the app is addressed

- Routes: `/w/{ws}/c/{channelId}` channel, `/w/{ws}/d/{dmId}` DM, `/w/{ws}/chat/saved`, `/w/{ws}/chat/mentions`, `/w/{ws}/directories?tab=people|channels`, `/w/{ws}/calendar`, `/w/{ws}/calls`, `/w/{ws}/files`, `/w/{ws}/settings/{account|privacy|sessions|appearance|notifications|about|profile|calls|security|company|workspace|roles}`, `/w/{ws}/settings/admin/{company|members|invites|workspaces|audit-log|company-roles|system-settings}`. `?thread=<msgId>` opens a thread panel; `?m=<msgId>` deep-links a message.
- API base `/api/v1`; errors are `{"code","key","message","trace_id"}`. Frequently used: `POST /messaging/messages {channel_id, body}`, `GET /messaging/channels/{id}/messages?limit=≤100`, `GET /messaging/messages/{id}/thread?limit=≤100` (returns `{parent, replies}`, not `messages`), `GET /search?q&company_id&workspace_id`, `GET /workspaces/{ws}/presence|unread|channels`, `GET /users/me/files?workspace_id&scope=own`, `POST /calendar/meetings`, `POST /messaging/users/block|unblock`, `POST /channels/{id}/archive`, `GET /users/me/channels/archived`.
- Calls: `/w/{ws}/calls` hub, `/w/{ws}/call/{id}` in-call, `/w/{ws}/calls/{id}` details (recording/chat/logs tabs). `GET /api/v1/meetings/current`, `GET /api/v1/workspace/{ws}/meetings/active` (not `/api/v1/meetings/active`). Settings are split: `PATCH /meeting/{id}` (name, password, approval) vs `PATCH /meeting/{id}/settings` (reactions, chat, device modes, guest link). Also `POST /meeting/{id}/invite|rating|cancel|messages`, `PUT /meeting/{id}/participants/{userId}` (device permissions). History is `GET /meetings/history?limit=≤100&before=<next_cursor>` (cursor-based, no type filter — the hub's All/Group/1-to-1 tabs filter client-side over loaded pages only). Scheduled meetings: `POST /calendar/meetings`, `POST /calendar/meetings/{id}/start`, `POST /calendar/meetings/{id}/respond {status}`. Bell entries: `GET /notifications?limit=N`.
- Messages are rendered from `[data-message-id]` elements; the composer is `div[contenteditable="true"][aria-label="Compose message"]` (Lexical). Bodies are stored markdown-escaped (`QA\-NET\-1`). **So print what the endpoint returned before searching it** — composer-typed bodies are escaped, API-posted ones are not, and a substring search for the unescaped form nearly produced "offline messages are silently lost" against messages that had arrived intact. The absence of a substring is a claim about the substring.
- **"Break the network" is not an instruction — how you broke it selects which branch of the product you tested.** Browser-offline and failed-request are different code paths here. `context.setOffline(true)`, where the browser *knows* it is offline, shows only "Waiting for network…" and the send queues and delivers by itself on reconnect. `page.route('**/…', r => r.abort('failed'))`, where the browser still believes it is online and one request dies, produces "Network error. Check your connection.", "Could not send the message. Try again." and "The server rejected this file". A finding measured on the second whose repro step says only "break the network" sends the reader to the first, where the behaviour is tidy, and comes back not-reproducible. Name the mechanism — a flapping link, a proxy, a blocked host — and put the other path in the measurement block as the control. Same shape as the WebRTC note below, one layer up.
- To fail requests, use Playwright (`browser_run_code_unsafe`), not a console `window.fetch` override — the app captures `fetch` at module load. `page.context().setOffline(true)` fails every request; `page.route('**/api/v1/…', r => r.abort('failed'))` fails one endpoint (`page.unroute` to undo). WebSocket behaviour under `setOffline` is unverified.

## How we work

- **Six distinct causes produce two observations, and from outside they are indistinguishable — which is why hitting one teaches you nothing about the next.** Each is documented separately in this file or in `SELECTORS.md`; this is the index to reach for when you have the symptom. *"The control is not there"*: a `label[for]` whose target holds no text; an element below a scrollable dialog's fold, where the hit test returns what is scrolled over it; the wrong testid, which returns zero elements rather than an error; a row container matched too small (no controls) or too large (wrong person). *"The control does nothing"*: `element.click()` on a pointer-driven control; or a name read as a state, without `disabled`/`aria-disabled`. One session had causes one and two hit the **same** control from different directions, which is why three attempts failed before the fourth worked.
- **The commonest false negative is a filter that excluded the thing you were looking for** — not an error, not an empty page, but a clean, confident, plausible result. A container probe that names the wrong element type, a text filter that drops inputs and icon buttons, a hit test that rejects anything below the fold, an exact-match regex against a label that carries a count, an ancestor walk that stops above the controls. Every one returns something that looks like an answer. **The remedy is the positive control**: it is cheap, and in the session that catalogued this it worked every single time it was used.
- **A verification result that agrees with your prior is the one you check least — and a broken instrument produces agreement as readily as disagreement.** Three separate cases tonight had that shape: a text locator that clicked the wrong node and returned a result matching the ticket being verified; a `grep` whose `\|` was a literal string under BSD and returned a count that appeared to refute a confirmed finding; and a truncated print that agreed with "no error was shown". **The cheap defence is that the instrument must be checkable independently of the claim** — a grep you can re-run with `-F`, an enumeration you can print in full, a scan taken before the action as well as after. If the only way to test the instrument is to trust the result, you have no instrument.
- **When a shared dependency changed mid-run and parity cannot be proven, check whether the change split your series.** Measurements taken entirely on one side of the edit are comparable to each other even if the behaviour did move; a series straddling it is not. That is a weaker answer than a diff, and it is available when a file is untracked.
- **A measurement can be correct while the description of what was measured is wrong — and no check on the measurement will catch it.** One sector hit this three times in a night: a truncated enumeration (the capture was right, the print was not), a complete enumeration of the wrong *set of surfaces* (every enumeration clean, the list of places truncated), and a comparison row labelled `/workspace/invite/accept?token=<dead>` that was actually measuring `/login`, because that URL redirects. **All three pass every check you can run on the measurement itself, because the measurement is not the broken part.** The check is to state what you believe you loaded and confirm it separately — the final URL, the surface's own identity, the bound of the set — before the number means anything.
- **A failure that is uniform across a whole set is the environment, not the code.** Twelve of twelve, eighteen of eighteen, nought of six — when everything fails the same way, stop reading the code and look at what they share. In one afternoon that shape was `timeout` not existing on macOS (every invocation "command not found", reported as eighteen broken snippets), a per-lane browser cap refusing the fourth account, and one leftover meeting blocking every later one, because a second call will not start while one is active. The converse is as useful: **a result that contradicts an earlier measurement means something changed between them**, not that one of them was wrong. A run reporting 19/19 and then 8/19 was correct both times, either side of a language switch.
- **Running a snippet after another snippet is not the same as running it alone, and the difference is invisible.** Handover snippets leave the app in the state being judged — a call still live, a co-host promoted, the interface in another language — and the next one starts from there. Every "broken snippet" chased in one afternoon was this, none was the script: a host cannot moderate a co-host, so the menu comes back empty; an account left in Uzbek fails every English selector; a meeting still active server-side blocks the next call while the window looks clean. `snip/_reset.mjs` puts one browser back to neutral and the bench runs it over **every** account a finding names before each go — ending a meeting strands the *other* windows on "Call has ended", so resetting only the one you drive is not enough. Drive snippets by hand in sequence and you must do the same.

- **A probe that finds nothing is a claim about your instrument before it is a claim about the app.** Before writing "X is absent / missing / broken / does nothing", say what would have had to be true for your probe to see X, and check that instead. Three sectors derived this independently on the same day from twenty-five near-misses, and essentially none of those was flaky product behaviour — every one was the measurement. `PITFALLS.md` is the catalogue of how they died; read it at session start.
- **A key-union over API responses proves absence only if the sample provably contains the case that would carry the key.** With `omitempty` anywhere in the stack, "I read 100 responses and the field was never there" is the same observation whether the field is unimplemented or merely never populated for those rows. One sector sampled 100 history rows on an account whose calls had all ended normally, found `end_reason` absent from every one, and nearly wrote that the payload carries no outcome field at all; on another account it appears in 9 of 100. Split the sample by the dimension that would carry the key *before* concluding — it is what turns a wrong absolute into a correct conditional.
- **When a negative holds for the party it cannot possibly apply to, the probe is wrong, not the product.** Every access, visibility or scoping finding has someone for whom the defect must not hold — the uploader, the owner, the sender, the person who performed the action. Run the same probe against them. It costs one call and it separates "the feature is broken" from "my filter is wrong", which is the distinction the instrument rule above asks for but does not tell you how to get. A probe filtering DM files on `context_id` came back empty for both participants and read as the defect holding; the tell was that the **uploader** also appeared to have no DM files of her own. DM files carry no `context_id` at all — the link lives in `shared_with`.
- **Measure, don't eyeball.** Every finding carries the request, response, or DOM measurement that proves it. Plausible-looking defects — slow loads, mispositioned elements, stray debug panels — have repeatedly evaporated under measurement.
- **Snapshot the other side continuously, from before the action.** Poll at ~300 ms starting before the trigger, and don't cap the sample — capped element lists and after-the-fact checks have repeatedly hidden a prompt, a marker or a toast and made working behaviour look broken. Select notifications by visibility, not by `role="status"` — that also matches an invisible `sr-only` live region.
- **A call surface, an incoming banner, a toast and the bell all live outside `main`, so `main` is never the right scope for observing a call event.** Two separate sessions nearly filed "invitations are not delivered" against working code from a poller scoped to `main`.
- **Measure a notice by polling from before the trigger and keeping the maximum opacity over its lifetime.** One sample after the action misses a toast that has already gone; recording only the first sighting catches it mid-fade-in at opacity 0. Both directions have produced false findings. Key each notice on text plus rounded size — a single toast matches both `[data-sonner-toast]` and `[role=alert]` — and tell a real notice from an `sr-only` companion by **size, not the hit test**: a 1×1 `sr-only` node passes `elementFromPoint` at its own centre.
- **Enumerating notifications only by `[role=status]`, `[role=alert]` or `[data-sonner-toast]` misses plain inline error text that carries no role**, and a rejected input then measures as a silent failure. Widen the scan to inline error nodes.
- **Restore state after a probe that failed, not just after a test that worked.** An inconclusive probe that leaves the UI changed is worse than its own null result, because the next measurement inherits the state silently and blames the product: one left a sidebar collapsed, and the following test reported "no Add channel" as though the control had been removed. The clean-up belongs in the probe, not in the test that comes after it. **And the leftover can be disguised by the very defect you were verifying**: a session muted a channel while re-checking a mute finding, spent three runs on "thread reply notifications never arrive", and the mute button read "Mute notifications" throughout — which was the defect they had just confirmed. Cost three runs and nearly withdrew a correct finding. **And when a probe did leave state, check whether it sits under something you have already published** — a session found an RSVP left changed pending→accepted beneath a published finding, re-ran that finding rather than assume the leftover was harmless, and it held from either state, which strengthened it. Assuming harmless is how a published finding quietly becomes unreproducible.
- **Re-verify the precondition, not only the conclusion — otherwise your own earlier testing will report a false collapse.** A finding said a screen offers no action when exactly one session exists; re-run late it showed two enabled buttons, which read as the finding failing. An earlier session-expiry test had left the account on two sessions — at which point the buttons appearing is **the finding's own control**, not a contradiction. Reduced to one, zero controls, finding intact. The failure direction here is withdrawing something correct, which nothing else catches.
- **Reproduce before writing up.** Run the same check at least twice and probe the boundary — different timing, entry point, settled vs fresh state — before describing behaviour as unconditional. Intermittent and state-gated defects read as absolute on a single run. **A rerun that disagrees with the first is the answer, not a failed attempt** — record both and describe the behaviour as varying, rather than running a third time until two agree. And a reproduction must repeat the **setup**, not just the actions: assert the precondition between steps, or a click that has silently become a no-op will produce numbers that mean nothing.
- **Before writing "the element/control isn't there", re-check on a freshly loaded page.** Client state in this app can lag the server, so a missing control may be stale state rather than product behaviour. A finding published on that basis had to be withdrawn.
- **Decide which question you are asking before you read text off the page, because `innerText` and `textContent` each answer one and fail silently at the other.** *Is it on screen?* — enumerate elements and run the visibility check (rect, the `opacity` product up the ancestor chain, `elementFromPoint` at the element's own centre); `innerText` includes text no user can see, and this app parks the generic channel-onboarding copy behind an `opacity: 0` layer on ordinary channels, empty DMs and Saved Messages, so `main.innerText` reports "Start this channel · Add teammates…" on a personal notes page whose visible empty state is "Nothing saved yet". *What does the user read?* — `innerText`, on an element already proven visible; `textContent` misses `text-transform`, so a `SPAN` reading `OTHER` on screen has `textContent` `"Other"` and a search for the visible string returns zero matches page-wide. Four candidate findings died on these two in one day, in both directions.
- **Prove absence by enumerating elements, not by reading page text — and never truncate the list you are about to make a claim about.** A truncated `innerText` slice is not evidence a control is missing — list the visible `button`/`a` nodes in the area and say what the list contained. A published finding built on a cut-off text dump had to be withdrawn. **A complete enumeration of the wrong surfaces is still an absence claim built on a truncated list.** One session enumerated every interactive element on the finished-call detail page, the hub, the hub row on hover and the DM — all complete, no slicing — and concluded a control did not exist. It lives on the call-ended summary overlay, which appears once when a call ends and is then gone, so no after-the-fact enumeration can ever see it. Before writing that a control is absent, ask where it would live if the product were built sensibly, and enumerate *that*: anything scoped to an event that has just finished belongs on the transient surface, not the record of it. **And enumerate controls with their state, not just their presence** — a control's *name is not its state*. `Delete file` present in a menu and `Delete file` available are different facts, and reading the first as the second has produced a false authz finding. Capture `disabled` / `aria-disabled` in the same pass, then confirm a click actually fires a request; where it matters, check the API directly refuses too. **Slicing the enumeration is the same mistake again** — `buttons[-6:]` or `sorted(set(n))[:18]` truncates by position, and a portalled control sits wherever the portal put it, not where you expect. Enumerate fully, then filter by meaning, never by position. **Enumerating one tag type is the same mistake in a smaller costume** — a control missing as `input[type=time]` may be sitting right there as a button. Enumerate what is interactive, not what you expected the markup to be.
- **A click on the first visible control is not a completed action — for anything with a confirmation step, assert the resulting state.** Leaving a call is two steps: `Leave call` opens "Leave this call? … Cancel | Leave", and clicking only the first leaves you *in the call*. A session polled 6m47s with both parties still in, `stillInCall: true` on both. That withdrew a High: call duration looked wildly inflated and was correct — `call_duration_seconds` is the meeting lifetime, and the inflated readings were of a meeting nobody had left. **The snippet kit contains both behaviours behind similar names**, so check which one a measurement used. The one-line check is the state, not the intent: after the leave, assert the URL no longer matches `/call/`.
- **Before concluding an action did nothing, prove the action landed.** A click that never registered and a click that registered and changed nothing produce an identical observation — no request, no panel, no state change. Read the control's own selected or pressed state first — **but make sure it is the right attribute for that control's kind.** A menu trigger exposes `aria-expanded`, not `aria-pressed`; reading `aria-pressed` on one returns a stable `"false"` that looks like proof the action did nothing, so the check passes and confirms the wrong conclusion instead of catching it. If it exposes none, that is a reason to record the check as inconclusive and say how to probe it properly, not a reason to report a finding.
- **To measure a row, take the smallest element containing both the identifier and the control** — sort candidates by `textContent` length and pick the shortest that holds both. Too small and too large fail identically from outside: one sector matched a container holding only the avatar and name, concluded the row had no Call or Message control and called a ticket untestable; another matched a container spanning several rows and acted on the wrong person. Neither error announces itself, and "the control is missing" and "I selected the wrong box" are the same observation.
- **Record which questions you answered, not which controls you exercised — or you will re-derive your own work.** One sector's coverage index said "type tabs switch buckets without a redundant request": true, and silent on the fact that two of those buckets can never be non-empty. Hours later they worked that same defect up from scratch as a new candidate, measured it fully, and only caught it at the dedup step — against a ticket their own log had already named. "Exercised the control" and "answered the question" look identical in a coverage note and are not.
- **A sweep's rows are leads, not results, and the quiet positives are as often the finding as the loud negatives.** One sector recorded a row as "page renders, 0 controls" — accurate, boring, never opened. Behind it was the best behaviour on the screen: a read-only view listing everything, naming every action the holder lacks and saying what to ask an administrator for — one tab away from a tab that answers the equivalent grant with a blanket "Admin access required". That turned their finding from "the gate omits an operand" into "the graceful version exists on the same page and this tab does not use it". Open the rows you labelled and skimmed; that is where the value leaks.
- **Quote the acting account's live permissions in any access or visibility finding.** Such a finding is a claim about a role, and a role is mutable state your own earlier tests change — a co-host grant from ninety minutes ago silently survives into every later measurement. Reloading the client does not catch it: the role is current, just not the one you believe. Read `my-permissions` or the equivalent at the moment of measurement and put it in the finding.
- **Functional bugs come before security bugs.** The question that earns time is whether a feature does the right thing for the person using it — wrong results, silent failures, state that contradicts what the user was told. Deliberate authz and leak hunting is lower priority; don't open a session with it. A security or privacy defect found while testing normally is still logged and rated on its merits.
- **Races are out of scope.** Don't construct scenarios where two actors act at the same instant, and don't build harnesses to provoke them — such findings are timing-dependent and land as tickets nobody can confirm. Sequential multi-account testing (A acts, then B observes) is not a race and stays in scope.
- **Check whether staging is broken before blaming the product.** A 500 — or a **404 on a route the deployed frontend clearly calls** — is often environment drift, not a defect. The two halves of staging move separately, and a frontend calling an endpoint its backend does not yet have produces defect-shaped behaviour with no defect behind it; bracket the backend by probing two routes whose landing dates you know. For a 500: compare `schema_migrations` against the repo's migrations, and the live columns against what the failing query inserts. Getting this wrong files a Critical against code that is fine.
- **Some defects are invisible to any pass whose wall-clock does not cross a date boundary in the tester's zone, and a daytime timebox never crosses one.** The team runs on +05, so local and UTC dates disagree only between local midnight and 05:00 — a five-hour window most sessions never see. A run that happened to cross it found a view opening on the UTC date rather than the user's. **Do not wait for the hour: override the zone.** CDP `Emulation.setTimezoneOverride` puts local and UTC on opposite sides of midnight at any time of day, and comparing two zones that *agree* against one that *diverges*, at the same instant, is what turns a suspicious reading into a demonstration.
- **In a timeboxed run, read the clock before deciding scope.** Estimated elapsed time drifts badly over a long session; `TZ=Asia/Tashkent date` is one call and it is the only reliable answer.
- **In a timeboxed or unattended run, never block on a question.** Take the reversible option, write the assumption into the log, and surface it in the final summary for the user to overturn. A question with nobody at the keyboard costs the whole window.
- **Don't issue commands that can raise a permission prompt mid-run** — killing processes, deleting outside the scratchpad, anything outside the working tree. Defer housekeeping to the end of the run. A permission prompt waits for a human regardless of any tool timeout, so it stalls indefinitely.
- **Cap tool calls at ten minutes, and don't re-run one that returned nothing useful.** Skip it, note the skip in the log, continue testing. Never let a single tool hold up the pass.
- **Reload long-lived call participants periodically.** A tab that has been in a live call for an hour, through dozens of bans, room changes, recording cycles and screen shares, drifts — and produces state-wrong findings that do not reproduce on a fresh client. One run lost four investigations to this. Cheaper to reload than to withdraw.
- **Suspect the rig before the app.** A finding that depends on how the test was driven is not a finding: check window isolation, `document.visibilityState`, and whether a helper is hiding the truth (see `RTC_STATS`) before concluding the product is broken.

## Maintaining this file

Two kinds of line, and nothing else:

- **Environment** — fixtures, scripts, infrastructure, how to run things. Plain instructions, undated; they break loudly when wrong.
- **Method** — how we work. Written as a rule, but only once the same problem has cost us twice, or the conclusion follows from how the system is built rather than from one observation. A single surprise goes in the session log, never in here as a rule.
- No narrative. State the conclusion; evidence and reasoning live in the session log. If a line needs "because on <date> X happened", it belongs in the log.
- No measured values, counts, limits, error keys, or current-state notes — they drift with every release and belong in the session log. If a line states what the app *currently does*, it is in the wrong file.
- **Nothing that could limit future testing goes in without explicit approval** — no rule, constraint, prohibition, scope limit, "not testable", "don't", "never", "only" or "must", however well-evidenced. Propose the exact diff, wait for a yes, and only then write it. If in doubt whether a line limits testing, treat it as limiting.
